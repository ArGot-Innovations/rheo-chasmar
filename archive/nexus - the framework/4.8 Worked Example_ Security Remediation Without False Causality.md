## 4.8 Worked Example: Security Remediation Without False Causality

Consider a vault whose current projected state at time `t_0` contains:

```text
x_b = (
    weak_credentials=5,
    sensor_coverage=1,
    backup_health=1,
    ...
)
```

Assume that `sensor_coverage=1` denotes sufficient observability for the `weak_credentials` variable to be considered valid at this checkpoint.

The system proposes a remediation action:

```text
a_t = rotate_one_weak_credential
```

Before the action is executed, the remediation episode records both the observed pre-action state and the expected post-action condition. For example:

```text
observed_before:
    weak_credentials = 5

expected_after:
    weak_credentials = 4
```

This pre-action expectation is important. Without it, a later reduction in the observed weakness count may indicate improvement, but it cannot produce a genuine prediction-error-like quantity because there was no temporally prior prediction against which the outcome can be compared.

A naive controller might instead wait for the next state snapshot and compute:

```text
Delta_weak =
    weak_credentials_after
    - weak_credentials_before
```

If the next snapshot reported `4`, the controller might conclude:

```text
Delta_weak = 4 - 5 = -1
```

and attribute that improvement to the credential rotation.

That inference is only valid, however, if the before and after observations are sufficiently comparable and the relevant variable remains observable.

Suppose two events occur between `t_0` and the next checkpoint `t_1`:

1. the credential rotation succeeds, reducing the true weak-credential count from `5` to `4`;
2. the sensor responsible for measuring credential weakness fails before the next projected state is produced.

The underlying host condition may therefore be:

```text
true_weak_credentials = 4
```

while the system's epistemically valid projected state is:

```text
weak_credentials = UNAVAILABLE
```

The projected value must not be written as:

```text
weak_credentials = 0
```

and should not be silently substituted with any other numeric default.

This distinction is fundamental:

```text
UNAVAILABLE != 0
```

Zero means that the system observed the metric and determined that no weak credentials were present.

`UNAVAILABLE` means that the system cannot currently establish the value.

Those states have completely different semantic and causal meanings.

The post-action state at `t_1` may therefore be represented conceptually as:

```text
x_(t_1) = (
    weak_credentials=UNAVAILABLE,
    sensor_coverage=0,
    backup_health=1,
    ...
)
```

A correct temporal projector does not interpret the disappearance of a measurable weakness signal as evidence of successful remediation. Instead, it propagates the epistemic degradation explicitly:

```text
credential-hygiene outcome:
    UNRESOLVED / UNAVAILABLE

sensor-observability shift:
    NEGATIVE

novelty:
    HIGH

state comparability:
    INSUFFICIENT

remediation residual:
    UNAVAILABLE

RPE:
    UNAVAILABLE
```

The remediation episode therefore remains open.

Cyrae may increase uncertainty-, novelty-, or inhibition-like channels because the system has lost the ability to evaluate an important dimension of the state. What must not occur is positive remediation reinforcement merely because the previously observed pathology can no longer be seen.

In other words:

```text
loss of evidence != evidence of recovery
```

and:

```text
sensor blindness != successful remediation
```

This is a deliberate fail-closed property of the architecture.

### Restoration of observability

Suppose sensor coverage is restored at a later checkpoint `t_2`.

The newly projected state is:

```text
x_(t_2) = (
    weak_credentials=4,
    sensor_coverage=1,
    backup_health=1,
    ...
)
```

The system may now possess a post-action observation that is meaningfully comparable to the pre-action state.

The remediation episode contains:

```text
pre_action_observation:
    weak_credentials = 5

predicted_post_action:
    weak_credentials = 4

observed_post_action:
    weak_credentials = 4
```

A simple remediation prediction residual may then be evaluated as:

```text
delta_remediation =
    observed_post_action
    - predicted_post_action
```

giving:

```text
delta_remediation = 4 - 4 = 0
```

A zero residual here does not mean "no remediation occurred."

It means:

```text
observed outcome == predicted outcome
```

The actual improvement relative to the original condition is separately represented by:

```text
Delta_state = 4 - 5 = -1
```

These quantities answer different questions.

`Delta_state` asks:

> How did the observed condition change?

`delta_remediation` asks:

> How different was the observed outcome from the outcome predicted before the action?

The architecture must not collapse these two quantities into one.

### Causality remains stricter than temporal correlation

Even after observability returns, the system should not automatically conclude that the credential rotation caused every favorable state change observed at `t_2`.

Between `t_0` and `t_2`, other events may have occurred:

```text
credential rotation
sensor failure
sensor restoration
operator intervention
policy update
external account deletion
background reconciliation
other remediation actions
```

Accordingly, the remediation episode must retain provenance linking:

```text
pre-action state
        |
        v
predicted outcome
        |
        v
authorized action
        |
        v
intermediate events
        |
        v
post-action observation
```

Only observations belonging to a sufficiently resolved temporal and provenance trajectory are eligible for causal remediation evaluation.

Thus:

```text
temporal succession != causal attribution
```

and:

```text
state difference != remediation outcome
```

This is why Phase 5 does not define remediation RPE as arbitrary subtraction between two snapshots.

A genuine remediation prediction error requires, at minimum:

```text
1. a valid pre-action observation,
2. a prediction produced before the action,
3. an explicitly identified remediation action,
4. preservation of the prediction/action binding,
5. a post-action observation,
6. sufficient observability of the relevant variables,
7. a valid temporal/provenance trajectory connecting them,
8. explicit treatment of unresolved or confounding intermediate events.
```

Only after those conditions are satisfied can the architecture evaluate something structurally equivalent to:

```text
delta_e =
    observed_outcome_e
    - predicted_outcome_e
```

or, where an explicit value model exists:

```text
delta_t =
    r_t
    + gamma * V(s_(t+1))
    - V(s_t)
```

The current Cyrae-Lite architecture should therefore distinguish at least four separate signals:

```text
homeostatic error
    distance from an acceptable operating region

state-prediction error
    difference between predicted and observed future state

remediation outcome
    measured change associated with an intervention episode

remediation RPE
    deviation of the observed intervention outcome from its
    temporally prior predicted outcome
```

None of these should be inferred merely because one vector differs from another.

The deeper architectural lesson is that temporal causality is not primarily an arithmetic operation. It is a provenance, observability, episode-binding, and comparability contract over state transitions.

Vector subtraction may participate in the final calculation, but it is only meaningful after the system has established that the two quantities being subtracted belong to the same causally interpretable episode.

The governing rule is therefore:

```text
no valid temporal lineage
        ->
no valid causal comparison
        ->
no remediation RPE
```

This prevents the system from rewarding itself for missing data, sensor failure, unrelated state changes, or post hoc explanations of outcomes that were never predicted in advance.
