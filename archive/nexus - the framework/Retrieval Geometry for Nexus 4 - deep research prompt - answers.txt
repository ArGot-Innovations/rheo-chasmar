# Retrieval Geometry for Nexus 4: Metric, Pseudometric, Quasimetric, Kernel, and Compatibility Requirements for HTLA/HTNLA Similarity and ANN/HNSW Search

## A. Executive Conclusion

### 1. Does HNSW require triangle inequality?

**FALSE as a formal requirement. CONTEXT-DEPENDENT as a practical matter.**

HNSW does not formally require the triangle inequality for execution. The algorithm can run with arbitrary dissimilarity functions that return a scalar ordering. However, the **theoretical analysis, greedy traversal guarantees, and optimal performance regimes** of HNSW assume metric structure.

The critical distinction is:

| Level | Triangle Inequality Status |
|-------|---------------------------|
| Algorithm execution | NOT required |
| Implementation APIs | NOT required (accept arbitrary callables) |
| Theoretical analysis | ASSUMED for complexity and correctness proofs |
| Search heuristics | EXPLOITED for pruning and navigation |
| Empirical recall | STRONGLY BENEFICIAL but not strictly necessary |

### 2. What properties does HNSW actually require?

HNSW requires, at minimum:

1. **A total order** over distances/scores for a fixed query (to rank neighbors)
2. **Consistency**: `d(x,y)` should be deterministic and stable
3. **Comparability**: distances from different candidates must be meaningfully comparable

It does **not** formally require:
- Non-negativity
- Identity of indiscernibles
- Symmetry
- Triangle inequality

### 3. What properties materially improve its behavior?

The following properties materially improve HNSW behavior without being formal requirements:

1. **Local metric structure** — even if global metricity fails, local approximate metricity aids greedy navigation
2. **Bounded distortion** — relaxed triangle inequality with constant `c` preserves many guarantees
3. **Smoothness** — small changes in input should produce small changes in distance
4. **Reasonable neighborhood structure** — points that are close should share neighbors

### 4. What geometry should Nexus require for ordinary HVD similarity retrieval?

For **ordinary HVD similarity retrieval**, Nexus should require:

**At minimum**: A well-defined distance or similarity function with:
- Deterministic evaluation
- Meaningful ranking behavior validated against exact search
- Documented geometry class

**Preferably**: A metric or metric-transformable geometry (Euclidean, angular, or cosine with normalization)

**For cosine similarity specifically**: Normalize vectors and use angular distance or `1 - cosine_similarity`, which preserves ranking and can be made metric.

### 5. What should Nexus do with asymmetric cross-label compatibility?

**Do NOT use standard HNSW directly for asymmetric cross-label compatibility.**

For asymmetric scores, Nexus should:

1. **Detect asymmetry** through validation tests
2. **Choose appropriate index strategy**:
   - If asymmetry is mild: consider symmetrization (`d_sym(x,y) = (d(x,y) + d(y,x))/2`)
   - If asymmetry is semantically meaningful: use **separate query and database encoders** or **MIPS-style reductions**
   - If asymmetry is severe: use **exact scan** or **specialized asymmetric ANN methods**
3. **Never silently treat asymmetric scores as metrics**

## B. Mathematical Taxonomy

### Metric

A function `d: X × X → ℝ` satisfying:
1. Non-negativity: `d(x,y) ≥ 0`
2. Identity of indiscernibles: `d(x,y) = 0 iff x = y`
3. Symmetry: `d(x,y) = d(y,x)`
4. Triangle inequality: `d(x,z) ≤ d(x,y) + d(y,z)`

**Status**: Strongest structure. Provides all theoretical guarantees.

### Pseudometric

Satisfies metric axioms except identity of indiscernibles: `d(x,y) = 0` allowed for distinct `x,y`.

**Status**: May be acceptable if the equivalence classes are harmless.

### Semimetric

Satisfies metric axioms **except** the triangle inequality (symmetry retained).

**Terminology note**: Literature varies. Some use "semimetric" for symmetry+identity+non-negativity without triangle inequality; others use it for weaker structures.

### Quasimetric / Quasi-metric

Satisfies metric axioms **except** symmetry: `d(x,y) ≠ d(y,x)` allowed, but a directed triangle inequality may still hold.

**Status**: May be usable with directed graph structures, but standard HNSW is undirected and assumes symmetric navigation.

### Divergence

Asymmetric, non-metric similarity measure. Example: KL divergence `D_KL(p || q)`

**Status**: Requires specialized handling. Standard HNSW may work empirically but without guarantees.

### Positive Semidefinite Kernel

`K(x,y)` such that the Gram matrix is PSD for any finite set. Corresponds to an inner product in a feature space.

**Status**: If `K` is PSD and normalized, it induces a metric via `d(x,y) = sqrt(K(x,x) + K(y,y) - 2K(x,y))`.

### Indefinite Kernel / Similarity

`K(x,y)` with both positive and negative eigenvalues.

**Status**: Does **not** induce a metric. Use with caution. May still be usable for MIPS-style retrieval.

### Maximum Inner Product Search (MIPS)

Find `argmax_y x^T y`. Not a metric problem in general.

**Status**: Can be reduced to nearest neighbor search via transformation (adding a dimension), or handled by ip-NSW variants.

## C. HNSW Requirements: Theorem, Implementation, and Empirical Behavior

### What the Original HNSW Paper Says

The original HNSW paper (Malkov & Yashunin, 2016) presents the algorithm as a **general metric space search index**. The theoretical analysis assumes:

- A metric distance function
- The existence of Delaunay graphs in the metric space
- Greedy traversal properties that rely on metric structure

**Critical observation**: The paper does **not** prove that HNSW requires a metric for correctness. It proves that HNSW works well in metric spaces. The distinction is load-bearing.

### What Implementation APIs Permit

Major implementations accept a wide range of distance functions:

| Implementation | Supported Metrics |
|---------------|-------------------|
| hnswlib | L1, L2, Cosine, Jaccard, Hamming |
| FAISS | L2, Inner Product (with normalization for cosine) |
| NMSLIB | Exotic distances including non-metric |
| Vespa | DotProduct (MIPS), Angular, Euclidean |

**Key finding**: Implementations routinely support cosine distance, which **does not** satisfy the triangle inequality.

### What Theoretical Analyses Assume

Theoretical analyses of HNSW typically assume metric structure for:
- Complexity bounds
- Greedy search correctness
- Graph construction properties

**Example**: The Slipstream analysis explicitly assumes `d(·,·)` is a metric to derive distance bounds.

### What Search Heuristics Exploit

HNSW's neighbor selection heuristics exploit:

1. **Diversity**: Selected neighbors should be diverse in direction (for metric cases)
2. **Proximity**: Closer neighbors are preferred
3. **Relative neighborhood**: Edges should approximate Delaunay graph structure

These heuristics are **designed for metric spaces** but can be applied to non-metric functions.

### What Is Needed for Reliable Empirical Recall

Empirical evidence shows:

1. **HNSW works on non-metric spaces** in practice
2. **Performance degrades** with severe non-metricity
3. **Transformations can restore geometry**: A query-agnostic spherical transformation raised HNSW recall above 95% on previously problematic datasets
4. **ip-NSW** (inner product HNSW) demonstrates that HNSW can be adapted to MIPS, but the hierarchical structure provides **less benefit** for MIPS than for metric search

### Classification of the Statement "HNSW depends on the triangle inequality"

| Classification | Verdict |
|---------------|---------|
| TRUE | ❌ False as a formal requirement |
| PARTIALLY TRUE | ✅ The theory assumes it; performance benefits from it |
| CONTEXT-DEPENDENT | ✅ For some functions it works; for degenerate cases it fails |
| FALSE | ❌ False as an absolute statement |

**Precise answer**: HNSW does not **depend** on the triangle inequality for execution, but it **depends** on metric-like structure for its theoretical guarantees and optimal performance. The algorithm can execute with arbitrary scores, but recall may degrade unpredictably.

## D. HTLA Aligned-Label Retrieval: Strongest Appropriate Geometry

For aligned-label retrieval with positive weights:

```
B_w(H,K) = Σ_l w_l ⟨H_l, K_l⟩, w_l > 0
```

This induces:
- A **norm** `||H||_w = sqrt(Σ_l w_l ||H_l||²)`
- A **metric** `d_w(H,K) = ||H - K||_w`
- A **cosine similarity** that is valid

**Strongest appropriate geometry**: **Metric** (specifically, weighted Euclidean).

**Nexus should**: Use this as the canonical geometry for aligned-label retrieval. Document it as a metric. Use HNSW with L2 or angular distance.

## E. HTLA Cross-Label Retrieval: Geometry Classification

Cross-label compatibility:
```
C_W(H,K) = Σ_{l,m} w_{lm} ⟨P_{l→m} H_l, K_m⟩
```

### Classification by Properties

| Condition | Geometry Class | HNSW Suitability |
|-----------|---------------|------------------|
| `A = A^T`, `A ≻ 0` | Inner product / Metric | ✅ Full support |
| `A = A^T`, `A ⪰ 0` singular | PSD kernel / Seminorm | ⚠️ May work; check null space |
| `A = A^T`, indefinite | Indefinite kernel | ⚠️ Use with caution; MIPS possible |
| `A ≠ A^T` | Asymmetric / Directed | ❌ Not suitable for standard HNSW |

### Key Rules

1. **PSD does NOT automatically imply metric**. A PSD kernel induces a metric only via `d(x,y) = sqrt(K(x,x) + K(y,y) - 2K(x,y))`.

2. **Asymmetric scores are NOT quasimetrics** unless the quasimetric axioms (including directed triangle inequality) are established.

3. **Indefinite bilinear forms** may still be useful for MIPS-style retrieval.

## F. HTNLA Retrieval: Learned Transform Consequences

### Model Generation Consistency

When HTNLA transforms vectors:
```
y = F_θ(x)
```

The critical rule from the HTNLA paper:

> **"query transform generation must be compatible with index representation generation"**【HTNLA §9.3】

### Implications for ANN

1. **Index staleness**: If `θ` changes, the index built under `θ_old` becomes geometrically incompatible with queries under `θ_new`
2. **Required actions**: Model change requires index rebuild, dual-generation serving, or explicit compatibility bridge
3. **Geometry may change**: A nonlinear transform can change the effective geometry of the space, potentially breaking metric assumptions even if the original space was metric

### Recommendation

HTNLA transforms should:
1. **Declare their geometry class** after transformation
2. **Bind index to model generation**
3. **Provide validation** that the transformed space preserves the required geometry (or document the deviation)

## H. Triangle-Property Recommendation

### Nexus Should Require:

**For canonical HVD similarity retrieval**: **Ordinary triangle inequality** (metric geometry)

**For cross-label compatibility**:
- **If symmetric and PSD**: Convert to metric via `d(x,y) = sqrt(K(x,x) + K(y,y) - 2K(x,y))`
- **If asymmetric**: Do **not** use standard HNSW; use exact scan or specialized methods
- **If indefinite**: Document as MIPS or general compatibility; do not claim metric properties

### Relaxed Triangle Inequality

If a relaxed triangle inequality holds:
```
d(x,z) ≤ c[d(x,y) + d(y,z)], c ≥ 1
```
Then many metric guarantees survive with degraded constants. This may be acceptable for some Nexus use cases, but must be validated empirically.

### The Central Decision

> **Nexus should not force one global answer.** Different retrieval classes require different geometries:
>
> - **Aligned-label retrieval**: Metric (weighted Euclidean)
> - **Cross-label symmetric PSD**: Metric via kernel transform
> - **Cross-label asymmetric**: Specialized handling (not standard HNSW)
> - **MIPS**: Specialized ip-NSW or transformation to metric

### Strongest Opposing Case

### Nexus Response

These objections are valid but do not invalidate the recommended approach:

1. **HNSW works on non-metric scores** — True, but without guarantees. Nexus should distinguish between "works in practice" and "has theoretical guarantees."

2. **ip-NSW works** — True, but it's a **variant** of HNSW, not standard HNSW. Nexus should use ip-NSW or transformation for MIPS, not pretend standard HNSW handles it.

3. **PSD restrictions may be conservative** — Nexus can allow non-PSD scores but must **document** them as such and **validate** empirically.

4. **Asymmetry is semantically meaningful** — Nexus should preserve asymmetry but use **appropriate indexes** (exact scan, directed graphs, separate encoders).

5. **Empirical testing may be sufficient** — For production systems, empirical validation is essential. But Nexus should also document geometry class and known limitations.

### What Nexus Should Do Anyway

**The defensible middle**:

1. **Require geometry declarations** for all ANN functions
2. **Use metric geometry** for canonical HVD similarity (it's the strongest and best-supported)
3. **Support non-metric scores** but with explicit documentation and validation requirements
4. **Handle asymmetry separately** — do not force it into metric indexes
5. **Validate empirically** in all cases, regardless of theoretical guarantees
6. **Distinguish between what executes, what performs well, and what has guarantees**

## A. Executive Conclusion

**A.1. Does HNSW require the triangle inequality?**
**Classification: PARTIALLY TRUE / CONTEXT-DEPENDENT.**

HNSW does **not** require the triangle inequality as a strict *execution* requirement. The algorithm can be instantiated with any callable dissimilarity or similarity function that returns a comparable scalar. FAISS, hnswlib, Lucene, and NMSLIB all permit inner-product and cosine-similarity spaces, neither of which satisfies the ordinary triangle inequality in its raw form.

However, the original HNSW paper frames the index as a **"general metric space search index"** and the algorithm's *navigability guarantees*, *neighbor-selection heuristics*, and *pruning efficacy* are all analyzed under metric-space assumptions.   Subsequent literature explicitly warns that "non-metric similarity measures or asymmetric distance functions may violate these assumptions and lead to degraded performance or convergence issues."

Therefore:
- **Execution:** HNSW can *execute* with non-metric, asymmetric, or indefinite scores.
- **Theoretical guarantees:** The original poly-logarithmic navigability proof assumes a metric (in fact, a doubling-dimensional metric space).
- **Empirical behavior:** Severe non-metricity can cause local minima, hub formation, degraded recall, and unstable insertion ordering.

**A.2. What properties does HNSW actually require?**
At minimum, HNSW requires:
1. A **comparable scalar score** (distance or similarity) between any two vectors.
2. **Non-negativity** (for distances) or a bounded range (for similarities).
3. A **distinguishable "closest" relation** so that greedy/beam search can rank candidates.

What it does *not* formally require:
- Symmetry (though bidirectional edge insertion assumes it for connectivity).
- Triangle inequality (for execution).
- Identity of indiscernibles (pseudometrics are tolerated).
- Positive-definiteness of an underlying kernel.

**A.3. What properties materially improve HNSW behavior?**
- **Symmetry** (or mild asymmetry with a symmetrized graph construction).
- **A form of geometric navigability**: the "shortcutable" property that if a node is not near the query, one of its neighbors is closer.
- **Bounded expansion / low doubling dimension** (intrinsic dimensionality matters far more than triangle inequality per se).
- **Stable ranking under the score**: monotonic transforms of a metric preserve greedy decisions.

**A.4. What geometry should Nexus require for ordinary HVD similarity retrieval?**
For aligned-label, same-generation, weighted inner-product retrieval where weights are strictly positive and vectors are normalized, Nexus should declare an **angular metric** (arccos of cosine similarity) or a **Euclidean metric on normalized vectors**. `1 - cosine_similarity` must **not** be advertised as a metric; it violates triangle inequality.

**A.5. What should Nexus do with asymmetric cross-label compatibility?**
Asymmetric cross-label compatibility (e.g., evidence→hypothesis, sensor→latent) must **not** be silently routed through standard symmetric HNSW. Nexus should either:
1. **Symmetrize** the score for graph construction (losing directional semantics) and use it only for retrieval ranking, or
2. **Use a directed/quasimetric index family** (directed proximity graph, bipartite index, or separate query/database encoders), or
3. **Fall back to exact scan / brute-force ranking** with explicit latency contracts, or
4. **Transform the problem** (e.g., MIPS reduction with auxiliary dimension) if the score admits a monotone embedding.

## B. Mathematical Taxonomy

### B.1. Metric
A function \(d: \mathcal{X} \times \mathcal{X} \to \mathbb{R}_{\ge 0}\) satisfying:
- Non-negativity: \(d(x,y) \ge 0\)
- Identity: \(d(x,y) = 0 \iff x = y\)
- Symmetry: \(d(x,y) = d(y,x)\)
- Triangle inequality: \(d(x,z) \le d(x,y) + d(y,z)\)

**Status for Nexus:** Required only when the index family explicitly demands it (e.g., metric trees, certain LSH families).

### B.2. Pseudometric
Allows \(d(x,y)=0\) for distinct \(x,y\).
**Nexus relevance:** A cross-label seminorm (zero-weight components) induces a pseudometric. HNSW can execute, but exact-neighbor uniqueness is lost.

### B.3. Semimetric
A symmetric function satisfying non-negativity, identity, and \(d(x,y)=0 \iff x=y\), but **not necessarily** triangle inequality.
**Nexus relevance:** `1 - cos(x,y)` on the unit sphere is a semimetric but not a metric. Many practitioners mistakenly treat it as a distance.

### B.4. Quasimetric / Directed Distance
Satisfies all metric axioms except symmetry. A **quasimetric** satisfies a directed triangle inequality:
\[d(x,z) \le d(x,y) + d(y,z)\]
while \(d(x,y) \neq d(y,x)\) is permitted.
**Nexus relevance:** Cross-label compatibility \(C_W(H,K)\) with asymmetric weights \(w_{lm}\) is naturally a quasimetric candidate if the directed triangle condition can be established.

### B.5. Similarity (General)
A larger-is-better score \(s(x,y)\). No distance or metric structure is implied.
**Nexus relevance:** A raw cross-label bilinear form \(H^T A_W K\) with indefinite \(A_W\) is merely a similarity.

### B.6. Positive-Semidefinite (PSD) Kernel
A symmetric function \(K(x,y)\) such that for any finite set and coefficients, \(\sum_{i,j} c_i c_j K(x_i,x_j) \ge 0\).
**Nexus relevance:** If \(A_W\) is symmetric PSD, the cross-label form induces a valid inner product and hence a metric via the norm. If \(A_W\) is indefinite, it is **not** a kernel and does not correspond to an inner product in any Hilbert space.

### B.7. Indefinite Kernel / Similarity
A symmetric bilinear form with both positive and negative eigenvalues.
**Nexus relevance:** Indefinite similarities break the geometric assumptions of most ANN indexes. They can be used for exact ranking or in specially designed indefinite-kernel methods, but standard HNSW has no theoretical contract for them.

### B.8. Divergence
A function such as KL divergence \(D_{KL}(p\|q)\), which is asymmetric and non-metric.
**Nexus relevance:** Bregman divergences (including KL) are widely used in machine learning. NMSLIB explicitly supports Bregman divergences with HNSW, though the original HNSW theoretical guarantees do not cover them.

## C. HNSW Requirements: Theorem, Implementation, and Empirical Behavior

### C.1. What the original paper assumes
Malkov & Yashunin (2016) describe HNSW as a **"general metric space search index"** and analyze complexity under the assumption that exact Delaunay-like proximity graphs are built in a metric space. The poly-logarithmic search bound relies on the geometric progression of hops in a navigable graph, which is proved under metric-space assumptions (specifically, that the graph is built in a space with bounded expansion or doubling dimension).

### C.2. What the implementation APIs permit
- **hnswlib:** Supports `l2`, `ip`, `cosine` spaces. Cosine is implemented as inner product on normalized vectors.
- **FAISS:** Supports `METRIC_L2`, `METRIC_INNER_PRODUCT`, `METRIC_L1`, `METRIC_Canberra`, etc.
- **Lucene / OpenSearch:** Supports `l2`, `cosinesimil`, `innerproduct`.
- **NMSLIB:** Explicitly a **Non-Metric Space Library** supporting exotic distances including Bregman divergences.

**Conclusion:** Implementation APIs are **permissive**; they do not enforce metric axioms at compile time or runtime.

### C.3. What the construction heuristics exploit
HNSW's SELECT-NEIGHBORS heuristic (Algorithm 4) creates diverse connections by examining candidates from nearest to farthest and keeping a candidate only if it is closer to the base element than any already-connected candidate. This is a **relative neighborhood** / Delaunay-like pruning rule. It implicitly assumes that "closer to the base than any existing neighbor" is a meaningful, transitive geometric condition. In a severely non-metric space, this rule can select edges that do not improve navigability, leading to disconnected useful neighborhoods or local minima.

### C.4. What is needed for reliable empirical recall
Empirical studies show that HNSW recall degrades under:
- High intrinsic dimensionality (concentration of measure).
- Highly clustered or discontinuous distributions.
- Hub-skewed data (hubness phenomenon).
- Poor insertion order (early nodes becoming over-connected hubs).

These failure modes are **exacerbated** when the score lacks metric structure, because metric structure provides the geometric regularity that the greedy heuristic expects. However, the failures are empirical, not proof of impossibility.

### C.5. Classification of the statement
**"HNSW depends on the triangle inequality."**
- **Execution:** FALSE. HNSW executes with inner product, cosine, and Bregman divergences.
- **Theoretical guarantee:** TRUE for the original poly-logarithmic navigability proof.
- **Empirical robustness:** PARTIALLY TRUE. Violations can degrade recall and navigability, but the algorithm often still functions acceptably for mild violations.
- **Overall:** CONTEXT-DEPENDENT.

## D. HTLA Aligned-Label Retrieval

For aligned-label similarity within a single direct-sum space \(\mathcal H_L = \bigoplus_{\ell} \mathbb{R}^{n_\ell}\), with strictly positive weights \(w_\ell > 0\):

\[B_w(H,K) = \sum_\ell w_\ell \langle H_\ell, K_\ell \rangle\]

This induces a norm \(\|H\|_w = \sqrt{B_w(H,H)}\) and therefore a valid inner product. Normalized similarity is:

\[\operatorname{sim}_w(H,K) = \frac{B_w(H,K)}{\|H\|_w \|K\|_w}\]

**Geometry class:** This is a **cosine-type geometry** on the unit sphere in \(\mathcal H_L\). The appropriate metric is the **angular distance**:

\[d_{\text{angle}}(H,K) = \arccos(\operatorname{sim}_w(H,K))\]

**Nexus requirement:** For aligned-label retrieval backed by HNSW, Nexus should:
1. Normalize vectors to unit \(w\)-norm.
2. Use inner product (which equals cosine similarity on normalized vectors).
3. Internally treat the geometry as **angular metric** for contract purposes.
4. **Prohibit** advertising `1 - cosine_similarity` as the distance metric, because it violates triangle inequality.

## E. HTLA Cross-Label Retrieval

Cross-label compatibility:

\[C_W(H,K) = \sum_{\ell,m} w_{\ell m} \langle P_{\ell\to m} H_\ell, K_m \rangle\]

### E.1. When is it metric?
Only if the flattened operator \(A_W\) is symmetric positive definite. This requires:
- \(w_{\ell m} = w_{m \ell}\) (symmetric weights).
- \(P_{\ell\to m}\) forms a consistent symmetric block structure.
- \(A_W\) has no negative eigenvalues.

**Status:** Rare for arbitrary cross-label configurations. This is a **strong constraint**, not the default.

### E.2. When is it a PSD kernel?
If \(A_W = A_W^T\) and \(A_W \succeq 0\). Then \(C_W\) is an inner product on a subspace (a seminorm if singular).

### E.3. When is it indefinite?
If \(A_W\) has both positive and negative eigenvalues. Then:
- No valid norm is induced.
- No metric distance can be derived without additional structure.
- Cosine normalization is geometrically meaningless (the "norm" can be zero or imaginary).
- Standard HNSW has **no theoretical guarantee**.

### E.4. When is it directed/asymmetric?
If \(A_W \neq A_W^T\) or \(w_{\ell m} \neq w_{m \ell}\). Then:
- It is not an inner product.
- It may be a quasimetric if a directed triangle inequality holds.
- Standard symmetric HNSW assumes bidirectional edges; asymmetric scores create a mismatch between the score direction and graph topology.

### E.5. What should Nexus do?
Cross-label compatibility must be **classified** before index selection:
- **SPD aligned case:** Use standard HNSW with angular metric.
- **SPD but cross-label:** Use HNSW after verifying symmetry and PSDness (eigenvalue test).
- **Indefinite or asymmetric:** Do **not** silently use HNSW. Use exact scan, a directed graph index, or a MIPS reduction if applicable.

---

## F. HTNLA Retrieval

HTNLA introduces nonlinear maps \(\phi_t\) and optional k-WTA sparsification. The retrieval consequences are:

1. **Nonlinear transform changes geometry:** If the transform is not an isometry, distances in the transformed space are not distances in the original space.
2. **Model-generation binding:** An ANN index built on \(F_{\theta_g}(x)\) is only valid for queries transformed by a compatible generation \(F_{\theta_g}(q)\).
3. **Approximate geometry:** Low-rank approximations, quantization, and learned transforms all alter retrieval geometry. The index must carry metadata about the transform contract (rank, distortion, version).

**Nexus rule:** ANN index generation must bind to representation generation. A change in HTNLA parameters should trigger index invalidation or rebuild.

## H. Triangle-Property Recommendation

### H.1. Ordinary triangle inequality
**Required for:** Metric trees (VP-trees, ball trees, KD-trees with metric pruning), certain LSH families, and the original HNSW theoretical analysis.

### H.2. Relaxed triangle inequality
For constant \(c \ge 1\): \(d(x,z) \le c[d(x,y) + d(y,z)]\).
**Relevance:** DiskANN's Vamana graph uses a **scaled triangle inequality** with parameter \(\alpha > 1\) for relaxed pruning.   This shows that ANN methods can tolerate a *multiplicative slack* in the triangle property.

### H.3. Directed / quasimetric triangle inequality
\[d(x,z) \le d(x,y) + d(y,z)\] with asymmetry permitted.
**Relevance:** Sufficient for directed proximity graphs. QRL proves that quasimetric properties enable global bounds on value-function error.

### H.4. Four-point / negative-type properties
Euclidean embeddability and negative type are more natural for many ANN methods than triangle inequality alone. Johnson-Lindenstrauss embeddings preserve finite-set Euclidean geometry without requiring the input to be a metric space.

### H.5. Monotonic ordering
If \(s(x,y) = f(d(x,y))\) for strictly monotone \(f\), ranking is preserved. HNSW greedy search only needs a **consistent ranking** of neighbors, not a metric. This is the weakest viable contract.

### H.6. Nexus canonical requirement
Nexus should **not** impose one global triangle property. Instead:

| Retrieval Class | Required Triangle Property |
|---|---|
| Aligned-label HVD (normalized) | Angular metric (strict TI on sphere) |
| Cross-label SPD kernel | Metric induced by norm |
| Cross-label indefinite | **None** — use exact scan or validated transform |
| Cross-label asymmetric | Directed TI if provable; else exact scan |
| MIPS | None — use specialized index or reduction |
| Divergence | None — use exact scan or Bregman-specific index |

1. **Undeclared geometry must not back an ANN index.**

8. **Empirical recall testing is necessary but not sufficient.**
   A passing benchmark does not convert a score into a metric.

## Required Adversarial Review

### Adversarial Case 1: HNSW performs well on strongly non-metric scores
**Evidence:** NMSLIB runs HNSW on Bregman divergences and KL divergence. FAISS runs HNSW on inner product. Empirical recall can be high.

**Rebuttal:** Execution is not guarantee. The original HNSW paper's complexity bound assumes a metric. Empirical high recall on specific datasets does not imply safety on all distributions. Hub formation and local minima are documented failure modes that become more likely with non-metric scores.

### Adversarial Case 2: Triangle inequality is irrelevant to graph ANN
**Evidence:** Proximity graphs like PSP achieve strong MIPS performance without relying on triangle inequality, using spherical pathways instead.

**Rebuttal:** PSP is a *specialized* graph designed for MIPS. It replaces the metric assumption with a different geometric structure (spherical pathways). This is not a license to drop any geometric requirement from HNSW; it is evidence that **different retrieval contracts need different indexes**.

### Adversarial Case 3: PSD restrictions are unnecessarily conservative
**Evidence:** Indefinite kernels can be decomposed into positive and negative parts and used in specialized SVMs. Perhaps a similar decomposition could feed an ANN index.

**Rebuttal:** No widely deployed ANN library (FAISS, hnswlib, Lucene, pgvector) supports indefinite kernels natively. Until a kernelized graph index with indefinite support is implemented and benchmarked for Nexus workloads, conservatism is warranted.

### Adversarial Case 4: Symmetrizing a directional score destroys useful semantics
**Evidence:** In evidence→hypothesis retrieval, the direction is semantically load-bearing. Symmetrizing collapses source and target roles.

**Rebuttal:** This is exactly why Nexus must **not** force symmetrization. Instead, it must offer a **directed index family** or exact scan for asymmetric cases. The adversarial case supports the engineering law, not its negation.

### Adversarial Case 5: MIPS reductions distort cross-label meaning
**Evidence:** Adding an auxiliary dimension to reduce MIPS to Euclidean changes the vector space and can create anisotropic distributions that are harder to index.

**Rebuttal:** The distortion is real. Therefore Nexus should treat MIPS reduction as a **transformed retrieval space** with its own geometry generation and validation, not as a transparent drop-in replacement.

### Adversarial Case 6: Empirical recall testing may be sufficient without metric proofs
**Evidence:** Production systems routinely use HNSW with cosine similarity and inner product without proving metricity, and they achieve acceptable recall.

**Rebuttal:** Empirical testing on a held-out benchmark is **necessary** but **not sufficient** for a canonical contract. It proves behavior on the tested distribution, not on adversarial queries, out-of-distribution inputs, or future model generations. Nexus architecture requires a **verified mathematical contract** for load-bearing retrieval, not merely a historically lucky configuration.

## Final Synthesis

The defensible middle ground for Nexus 4 is:

> **HNSW executes with any comparable score, but its navigability heuristics, theoretical guarantees, and empirical robustness are designed for metric or near-metric geometry. Nexus must therefore declare the retrieval geometry explicitly, verify mathematical properties where possible, and route indefinite or asymmetric cross-label compatibility to appropriate index families (or exact scan) rather than silently forcing it through standard symmetric HNSW.**

This avoids both errors:
- Saying "HNSW requires a metric" (false for execution).
- Saying "HNSW accepts any callable score, therefore geometry does not matter" (false for guarantees and robustness).

The retrieval-geometry contract between HTLA/HTNLA and HVD ANN search is therefore a **typed, verified, and index-matched contract**, not a hope.

# Retrieval Geometry for Nexus 4
## Canonical contract for HTLA/HTNLA → HVD → ANN/HNSW

**Executive conclusion:** HNSW does **not** formally require the triangle inequality in order to execute, and major implementations support nonmetric objectives such as inner product. But “HNSW accepts the score” does not mean an arbitrary score yields a safe, navigable, or reliably high-recall graph. Nexus should require an explicit, verified **retrieval-geometry contract** before any ANN index is built, with ordinary metric geometry as the default for same-space similarity retrieval, a separate MIPS contract for valid bilinear scores, and a distinct directed-compatibility contract for asymmetric cross-label retrieval.

The statement **“HNSW depends on the triangle inequality” is CONTEXT-DEPENDENT**:

- **False** as an execution/API requirement: HNSW can be implemented as repeated scoring, candidate maintenance, and graph traversal; FAISS, Lucene/OpenSearch, and hnswlib-family systems support inner product and cosine-style objectives, even though raw inner product is not a metric and common cosine dissimilarity \(1-\cos\) fails triangle inequality. [github](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)
- **True** for metric-tree-style exact pruning and for any HNSW extension that derives valid lower bounds from graph edges using triangle inequality.
- **Partly true** as a performance claim: HNSW’s greedy navigation and heuristic neighbor selection are designed around local proximity structure. A metric—especially one with favorable intrinsic dimension and cluster/manifold structure—usually makes that graph easier to navigate and makes quality more predictable. This is not equivalent to saying triangle inequality is an HNSW precondition.
- **A Nexus design preference:** ordinary same-space retrieval should prefer a proven metric or a rigorously equivalent monotone representation. Nonmetric retrieval is allowed only under an explicitly different contract, with stronger benchmark obligations and exact reranking.

The central Nexus rule should be:

> **An arbitrary compatibility score may be used for exact candidate ranking, but it must not be silently declared an ANN distance or supplied to a graph index without a declared geometry class, supported-index proof, and measured recall contract.**

# 1. Mathematical taxonomy

## Core definitions

Let \(X\) be a set and \(d:X\times X\to\mathbb{R}\).

| Structure | Conditions | Retrieval interpretation |
|---|---|---|
| **Metric** | \(d(x,y)\ge0\); \(d(x,y)=0\Leftrightarrow x=y\); \(d(x,y)=d(y,x)\); \(d(x,z)\le d(x,y)+d(y,z)\) | Full ordinary nearest-neighbor geometry |
| **Pseudometric** | Metric axioms except \(d(x,y)=0\) may hold for \(x\ne y\) | Retrieval geometry on equivalence classes; useful when representations intentionally collapse distinctions |
| **Semimetric** | Terminology is inconsistent | Nexus should not use this unqualified label |
| **Quasimetric / quasi-metric** | Usually \(d(x,x)=0\), \(d(x,z)\le d(x,y)+d(y,z)\), but symmetry is not required; some authors relax or alter separation conditions | Directed retrieval can potentially use it, but only after directed triangle and orientation semantics are proved |
| **Relaxed quasi-metric / \(c\)-quasimetric** | \(d(x,z)\le c[d(x,y)+d(y,z)]\), \(c\ge1\) | May permit specialized approximate theory; do not treat as a standard metric |
| **Dissimilarity** | Any lower-is-better function | May support ranking but no geometric consequences follow |
| **Similarity** | Any higher-is-better function | May be symmetric or asymmetric; may be bounded or unbounded; need not define a distance |
| **Kernel** | A symmetric \(K\) whose every finite Gram matrix is PSD | Corresponds to an inner product in a Hilbert feature space |
| **Indefinite kernel** | Symmetric but some Gram matrix has negative eigenvalues | Does not define a Hilbert inner product; ordinary kernel-distance interpretation fails |
| **Divergence** | Often nonnegative and separating but not symmetric and not triangular | Example: \(D_{\mathrm{KL}}(p\|q)\); directional information-loss or fit score, not an ordinary distance |
| **MIPS score** | \(s(q,x)=q^\top x\), maximize | A ranking objective, not a metric in general |
| **Directed compatibility** | \(C(q,x)\), possibly asymmetric and indefinite | A task score; requires a query-side/candidate-side retrieval contract |

### Why “semimetric” must be banned unless qualified

The word **semimetric** has incompatible usages:

- In some mathematical texts, it means a symmetric nonnegative function satisfying identity of indiscernibles but **not necessarily** triangle inequality.
- In other contexts it is used for a pseudometric.
- In applied similarity-search systems it can be used loosely for any nonmetric dissimilarity.

**Nexus recommendation:** prohibit bare `SEMIMETRIC` from the type system. Replace it with explicit properties:

```text
NONNEGATIVE
SEPARATING
SYMMETRIC
TRIANGULAR
RELAXED_TRIANGLE_CONSTANT = c | UNKNOWN
DIRECTIONAL
```

A name must never hide the missing axiom.

## Similarity versus distance

A strict monotone transform preserves the exact rank ordering for a fixed query:

\[
s(q,x)=f(d(q,x)),
\]

where \(f\) is strictly decreasing, or equivalently

\[
d(q,x)=g(s(q,x)),
\]

where \(g\) is strictly decreasing over the score range.

This gives an important but limited fact:

> **Rank equivalence is sufficient for exact top-\(k\) ranking, but it does not automatically preserve every geometric property used by an index.**

For example:

- If \(d\) is a metric and \(f\) is strictly monotone, ranking is unchanged.
- But the transformed score need not be a metric.
- Squaring Euclidean distance preserves rankings but generally destroys triangle inequality.
- HNSW can often still work with squared \(L_2\) because its traversal compares score order rather than performing metric lower-bound pruning.
- A metric tree that needs triangle-inequality bounds cannot safely treat squared \(L_2\) as though it were Euclidean distance.

This distinction is crucial for Nexus: **ranking preservation and metric preservation are different contracts.**

***

## Kernels and distances

A symmetric kernel \(K\) is PSD when every finite Gram matrix

\[
G_{ij}=K(x_i,x_j)
\]

is positive semidefinite:

\[
\sum_{i,j} c_i c_j K(x_i,x_j)\ge0
\]

for all finite selections and all real coefficient vectors \(c\).

Then there is a Hilbert-space feature map \(\phi\) such that

\[
K(x,y)=\langle\phi(x),\phi(y)\rangle.
\]

A corresponding feature-space squared distance is

\[
d_K^2(x,y)
=
K(x,x)+K(y,y)-2K(x,y).
\]

Important limitations:

- If \(K\) is PSD but singular, then distinct states may map to the same feature vector; \(d_K\) is a **pseudometric**, not necessarily a metric.
- If \(K\) is strictly positive definite over the declared representation domain, the induced feature-space distance is a metric there.
- If \(K\) is indefinite, the expression above can be negative and cannot be treated as squared Euclidean distance.
- A PSD kernel is not itself a distance. It is an inner-product-like similarity structure.

A conditionally negative-definite function can be useful because, under appropriate normalization, it often yields Hilbert-space squared distances and permits exponentiated PSD kernels. That is a route to a valid geometry, but only if the theorem’s domain and normalization conditions are actually met. Finite sampled eigenvalue checks can detect violations but cannot establish a universal property of an arbitrary nonlinear score. [arxiv](https://arxiv.org/html/1807.03555v1)

# 2. What HNSW actually requires

## Four different senses of “requires”

HNSW discussions often collapse four distinct ideas. Nexus should keep them separate.

| Layer | Question | Triangle inequality required? | Nexus implication |
|---|---|---:|---|
| **Execution** | Can the code compute scores, maintain candidate queues, choose neighbors, and traverse a graph? | No | A callable score can be executed if it is finite and ordered |
| **Implementation API** | Does the library expose that score/space? | Library-specific | Use only documented space types or a tested custom implementation |
| **Formal theory** | Does a theorem guarantee pruning, approximation, connectivity, or complexity? | Often yes for metric theorems | Do not borrow metric guarantees for nonmetric scores |
| **Heuristic performance** | Does the constructed graph remain navigable and achieve recall at target latency? | Not logically required, often helpful | Measure it against exact score ranking on Nexus workloads |

The HNSW architecture creates multiple layers of proximity graphs, with upper layers for large-scale navigation and lower layers for local candidate refinement. Randomly assigned maximum layers create exponentially fewer elements in upper levels, analogous to the hierarchy of a skip list. [arxiv](https://arxiv.org/abs/1603.09320)

At search time, a conventional HNSW implementation:

1. Starts at an entry point in the top layer.
2. Greedily moves to a neighbor that improves the query score.
3. Descends layers.
4. At the base layer, explores a bounded candidate frontier—controlled by `ef_search`—and returns the best candidates discovered.

At insertion time, it:

1. Searches existing layers for candidate neighbors.
2. Selects a bounded number of links according to an approximate neighbor/diversification heuristic.
3. Adds bidirectional links in standard implementations.
4. Prunes excess neighbors to maintain degree bounds.

None of those primitive data-structure operations requires a triangle inequality. They require at minimum:

- a score computable for query–node and usually node–node pairs;
- an unambiguous ordering direction—lower is better or higher is better;
- finite numerical values;
- deterministic or explicitly specified handling of NaNs, infinities, ties, and self comparisons;
- a coherent query/database representation domain;
- often, though not mathematically inevitably, a meaningful score for **database-to-database** neighbor construction.

That last point is where arbitrary query-to-candidate compatibility gets dangerous.

***

## The hidden HNSW assumption: one geometry serves two roles

A standard HNSW graph normally uses one score relation in two distinct roles:

\[
\text{edge building: } d(x_i,x_j)
\]

and

\[
\text{query traversal: } d(q,x_i).
\]

This is harmless for ordinary symmetric metrics because database points and queries live in the same space and use the same geometry.

For a directional HTLA cross-label score

\[
C(q,x)\neq C(x,q),
\]

the symmetry failure is not merely a mathematical nicety. The question becomes:

> What does an edge \(x_i\to x_j\) mean when both endpoints are candidates, but the production objective is only query-source \(\rightarrow\) candidate-target compatibility?

A standard graph built from \(C(x_i,x_j)\) may encode a different relation than the production ranking \(C(q,x)\). If query and candidate domains differ semantically, \(C(x_i,x_j)\) may not even be defined. A naïve HNSW use is therefore architecturally invalid, even if the code can be forced to execute.

***

## Triangle inequality and HNSW heuristics

### What triangle inequality does not do

The ordinary HNSW search loop does not generally compute a lower bound such as

\[
d(q,u)\ge d(q,v)-d(v,u)
\]

and prune \(u\) solely from that bound. It directly evaluates candidate-query scores. Therefore the triangle inequality is not an operational prerequisite to visiting a neighbor, updating a queue, or selecting the currently best scored candidate.

This distinguishes HNSW from many **metric indexes**. Exact metric indexes use the triangle inequality to eliminate regions without evaluating all objects. Standard metric-space surveys define the indexed domain around symmetry, nonnegativity/separation, and triangle inequality precisely because their pruning validity rests on those axioms. [www-db.disi.unibo](https://www-db.disi.unibo.it/courses/SI-M/papers/HS03.pdf)

### What triangle inequality can improve

Metric structure can make the following HNSW properties more likely, though this is a heuristic and distribution-dependent claim:

- **Local coherence:** neighbors of a point tend to be mutually nearby.
- **Greedy progress:** moving toward a better local candidate tends to move toward the target’s neighborhood.
- **Multi-scale structure:** long links bridge regions while short links refine locally.
- **Diversification meaning:** relative-neighborhood-style pruning is more meaningful when “between” and “near” behave geometrically.
- **Stability under insertion:** nearby insertion candidates tend to establish useful links rather than score-arbitrary ones.
- **Fewer adversarial local minima:** graph paths tend to give improving routes to desired neighborhoods.

These are not universal theorems for arbitrary real datasets. HNSW quality depends heavily on intrinsic dimension, density variation, cluster structure, degree \(M\), construction beam `ef_construction`, query beam `ef_search`, score computation precision, and insertion order. Production documentation itself exposes the quality/latency tradeoff: larger candidate lists during construction and search raise graph accuracy/recall but consume more time and memory. [docs.opensearch](https://docs.opensearch.org/latest/mappings/supported-field-types/knn-methods-engines/)

### When triangle inequality becomes strictly relevant

It becomes an actual requirement when Nexus invokes any optimization or theorem that uses metric bounds, including:

- VP trees, cover trees, M-trees, GNAT-like metric indexes, ball trees under their metric assumptions;
- exact branch-and-bound using pivot distances;
- metric-spanner certification or graph-edge lower bounds;
- triangle-based candidate pruning;
- some metric LSH analyses;
- theoretical bounds parameterized by metric doubling dimension;
- any guarantee explicitly stated for a metric space.

A recent HNSW certification proposal, for example, derives lower bounds through the triangle inequality and explicitly restricts itself to distances that satisfy it directly or through a transform. Such a method is not evidence that base HNSW itself requires the triangle inequality; it illustrates that **additional exactness/certification layers do**. [arxiv](https://arxiv.org/html/2607.02338v1)

***

## Explicit counterexample: a nonmetric score HNSW can execute

Take unit vectors \(u,v\in \mathbb{R}^d\), with score

\[
d_{\cos}(u,v)=1-u^\top v.
\]

This is nonnegative and symmetric, but it fails triangle inequality. Let three unit vectors lie on a great-circle arc at angles \(0^\circ\), \(60^\circ\), and \(120^\circ\):

\[
d_{\cos}(0^\circ,120^\circ)=1-\cos 120^\circ=1.5,
\]

while

\[
d_{\cos}(0^\circ,60^\circ)+d_{\cos}(60^\circ,120^\circ)
=
0.5+0.5=1.
\]

So

\[
1.5 \nleq 1.
\]

Yet production ANN systems permit cosine-style HNSW retrieval. FAISS documents cosine search through unit normalization and maximum inner product; OpenSearch supports HNSW with `cosinesimil`, `innerproduct`, and \(L_2\), with supported combinations dependent on engine/version. [github](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)

Therefore:

> **“Triangle inequality is required for HNSW to run” is disproved by common HNSW deployment practice.**

But this is not a license for arbitrary scoring. The cosine case remains geometrically well behaved because unit-vector cosine ranking is equivalent to angular ranking and chordal Euclidean ranking—both true metrics—even if a particular reported score such as \(1-\cos\) is nonmetric.

# 3. Cosine geometry: the Nexus-safe formulation

## Distinguish the four objects

For nonzero vectors \(x,y\), define normalized directions

\[
\hat{x}=\frac{x}{\|x\|_2},
\qquad
\hat{y}=\frac{y}{\|y\|_2}.
\]

| Name | Definition | Metric? | Ranking relation |
|---|---|---:|---|
| Cosine similarity | \(\cos(x,y)=\hat{x}^{\top}\hat{y}\) | No; similarity | Larger is better |
| Cosine dissimilarity | \(1-\cos(x,y)\) | No; fails triangle | Smaller is better |
| Chordal distance | \(\|\hat{x}-\hat{y}\|_2=\sqrt{2-2\cos(x,y)}\) | Yes, on normalized vectors/directions | Same ordering as cosine |
| Angular distance | \(\arccos(\cos(x,y))\) | Yes, on directions | Same ordering as cosine |

The fact that \(1-\cos\) fails triangle inequality is not merely terminological. It is proportional to **squared** chordal Euclidean distance:

\[
1-\cos(x,y)
=
\frac{1}{2}\|\hat{x}-\hat{y}\|_2^2.
\]

Squaring preserves fixed-query rankings but not triangle inequality. The angular distance is a true spherical metric, and the chordal distance is a true Euclidean metric on the unit sphere. [arxiv](https://arxiv.org/pdf/2107.04071.pdf)

## What implementations actually do

FAISS describes cosine similarity as a larger-is-better similarity—not a distance—and maps it to maximum inner product by L2-normalizing both indexed vectors and query vectors. On normalized vectors,

\[
\|\hat{x}-\hat{y}\|_2^2=2-2\hat{x}^{\top}\hat{y},
\]

so maximum cosine, maximum normalized inner product, minimum squared \(L_2\), minimum chordal distance, and minimum angular distance all return the same ranking. [github](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)

OpenSearch documents HNSW support for \(L_2\), cosine similarity, and inner product across engines, and notes that its FAISS cosine mode automatically normalizes vectors during indexing because the underlying search is normalized inner product. [docs.opensearch](https://docs.opensearch.org/latest/mappings/supported-field-types/knn-methods-engines/)

### Nexus recommendation for aligned cosine-like HTLA

For aligned-label retrieval with strictly positive weights \(w_\ell>0\), define

\[
\langle H,K\rangle_w
=
\sum_\ell w_\ell \langle H_\ell,K_\ell\rangle,
\]

\[
\|H\|_w=\sqrt{\langle H,H\rangle_w}.
\]

This is an inner product and norm. Normalize valid nonzero states:

\[
\tilde H=\frac{H}{\|H\|_w}.
\]

Then choose one formal geometry:

- **Canonical metric semantics:** angular distance
  \[
  d_{\angle}(H,K)=\arccos\left(\langle\tilde H,\tilde K\rangle_w\right).
  \]
- **Implementation-equivalent ANN objective:** weighted normalized dot product or squared chordal \(L_2\).
- **User-facing score:** cosine similarity, clearly tagged as a similarity rather than a metric.

This preserves current cosine-like graded retrieval while making the formal geometry unambiguous.

### Zero vector policy

Cosine is undefined when either weighted norm is zero. Nexus must not silently make the convention

\[
\operatorname{cos}(0,x)=0
\]

part of the mathematical geometry. It may define an operational fallback, but that fallback must be declared:

```text
ZERO_NORM_POLICY =
  REJECT_QUERY
  EXCLUDE_CANDIDATE
  ROUTE_TO_SEPARATE_BUCKET
  RETURN_DEFINED_BASELINE_SCORE
```

A numerical epsilon in a denominator is a stability device, not a proof that cosine geometry exists for zero vectors.

# 4. HTLA cross-label operators

Let flattened HTLA states be \(H,K\in\mathbb{R}^N\), and define

\[
C_A(H,K)=H^\top A K.
\]

The type of \(A\) determines the available retrieval contract.

## Operator classification

| Operator condition | Mathematical object | Valid norm/distance? | Cosine normalization? | Retrieval classification |
|---|---|---|---|---|
| \(A=A^\top\succ0\) | Inner product | Yes: \(\|H\|_A=\sqrt{H^\top A H}\); \(d_A(H,K)=\sqrt{(H-K)^\top A(H-K)}\) | Yes | `MAHALANOBIS_METRIC` / `INNER_PRODUCT_GEOMETRY` |
| \(A=A^\top\succeq0\), singular | PSD bilinear form / kernel | Seminorm; induced pseudometric | Yes only after quotienting or accepting zero-norm equivalence classes | `PSD_KERNEL_PSEUDOMETRIC` |
| \(A=A^\top\), indefinite | Indefinite bilinear form | No norm from \(H^\top A H\); distance expression can fail | No ordinary cosine | `INDEFINITE_BILINEAR_SCORE` |
| \(A\ne A^\top\) | Directed bilinear compatibility | Not an inner product on the stated space | Not ordinary cosine | `DIRECTED_BILINEAR_SCORE` |
| \(A\ne A^\top\), but a separately proven directed distance is used | Potential quasimetric | Only if directed axioms are proven | Not ordinary cosine unless separately constructed | `QUASIMETRIC` |
| \(A=B^\top B\) | Explicit feature map \(BH\) | Euclidean metric after transform, if \(B\) injective; pseudometric otherwise | Yes in \(BH\) space | `EMBEDDED_L2` |
| \(A\) decomposed as PSD part plus residual directional/indefinite term | Hybrid score | Metric only for PSD component | Only for PSD component | two-stage retrieval |

### Symmetric positive-definite case

If

\[
A=A^\top
\qquad\text{and}\qquad
H^\top A H>0\ \text{for all }H\ne0,
\]

then \(A\) has a factorization

\[
A=L^\top L,
\]

such as a Cholesky factorization. Define the embedded representation:

\[
\phi_A(H)=LH.
\]

Then

\[
\langle H,K\rangle_A
=
\phi_A(H)^\top\phi_A(K)
\]

and

\[
d_A(H,K)
=
\|\phi_A(H)-\phi_A(K)\|_2.
\]

This is exactly the correct Nexus route from weighted/cross-label positive-definite compatibility to ordinary ANN geometry.

**Nexus action:** index \(LH\) with \(L_2\), or normalize \(LH\) and index with inner product/cosine if directional similarity is the intended semantics.

### Symmetric PSD case

If \(A\succeq0\) but has a nontrivial null space, then some nonzero \(H\) satisfy

\[
H^\top A H=0.
\]

The induced geometry is only a pseudometric:

\[
d_A(H,K)=0
\]

can occur for distinct states whose difference lies in \(\ker A\).

This can still be valid if Nexus explicitly intends to ignore those directions. But it is not identity-preserving retrieval. The index should record that the score geometry operates over a quotient space:

\[
H\sim K
\Longleftrightarrow
H-K\in\ker A.
\]

### Indefinite symmetric case

If \(A\) has both positive and negative eigenvalues, \(H^\top A H\) can be negative, zero for nonzero \(H\), or positive depending on direction. It is not a norm, and a standard \(A\)-cosine

\[
\frac{H^\top A K}
{\sqrt{H^\top A H}\sqrt{K^\top A K}}
\]

may be undefined or non-real.

Nexus must not call it:

- an inner product,
- a norm,
- cosine,
- Mahalanobis distance,
- a PSD kernel,
- or a metric.

It may still be a useful **general bilinear compatibility score**, but retrieval must be handled under the `GENERAL_SCORE` or a separately established MIPS-like contract.

### Asymmetric case

Write

\[
A=S+R,
\]

where

\[
S=\frac{A+A^\top}{2},
\qquad
R=\frac{A-A^\top}{2},
\qquad
R^\top=-R.
\]

Then

\[
H^\top A K
=
H^\top S K+H^\top R K.
\]

The symmetric part can potentially yield a valid geometry if \(S\succeq0\). The skew component encodes directional structure and cannot be recovered from a symmetric distance without discarding or changing semantics.

This decomposition suggests a principled hybrid design:

\[
\text{retrieve candidates using } \phi_S(H),
\]

then rerank by

\[
C_A(q,x)=q^\top A x.
\]

This is not mathematically exact unless the candidate set is sufficiently large or the directional residual is bounded relative to the metric surrogate. It must therefore be benchmarked and advertised as approximate directed retrieval—not as exact top-\(k\) compatibility search.

***

# 5. MIPS is not metric ANN

## The MIPS problem

Maximum inner product search is:

\[
\operatorname*{arg\,max}_{x\in\mathcal{D}}q^\top x.
\]

It is a ranking problem. Without restrictions such as unit normalization or bounded norms, it is not the same as nearest-neighbor search in a fixed symmetric metric.

For a fixed query \(q\), its norm scales every candidate score equally:

\[
(\alpha q)^\top x=\alpha(q^\top x),
\quad \alpha>0.
\]

But database vector norms affect rankings. Thus raw dot product rewards alignment and candidate magnitude. FAISS explicitly distinguishes inner product from cosine and notes that they agree only after normalizing vectors. [github](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)

## Valid reductions

Several reductions can convert MIPS to a metric or cosine-style problem under stated conditions:

- **Unit normalization:** turns inner product into cosine similarity, but changes the intended score if vector magnitude is meaningful.
- **Extra-coordinate Euclidean reduction:** when database norms are bounded, map database and query vectors into augmented spaces such that Euclidean nearest-neighbor order matches MIPS order.
- **Asymmetric transforms / ALSH:** use distinct query and database transformations to turn MIPS into angular or Euclidean retrieval.
- **Direct MIPS-capable ANN:** use an implementation that natively supports inner-product search.

FAISS documents both direct `METRIC_INNER_PRODUCT` and a one-extra-dimension reduction from inner product to \(L_2\), while cautioning that the reduction may interact poorly with quantization and other index structures.  Work on nonmetric similarity graphs for MIPS likewise shows that a transformation which is algebraically valid need not automatically produce the best graph behavior. [github](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)

## Nexus MIPS contract

Use a distinct retrieval class whenever the production objective is:

\[
s(q,x)=\phi_Q(q)^\top\phi_D(x),
\]

where \(\phi_Q\) and \(\phi_D\) may differ.

This includes:

- ordinary dot-product retrieval;
- query/data tower models;
- directional cross-label bilinear maps;
- evidence-to-hypothesis matching;
- source-to-target compatibility;
- some learned HTNLA query/candidate encoders.

Do **not** mislabel this as a metric merely because a library has an HNSW “inner product” option.

***

# 6. Asymmetric cross-label retrieval

## The core issue

For a directional production objective

\[
C(q,x)\ne C(x,q),
\]

there are at least four legitimate forms of retrieval architecture.

| Strategy | When appropriate | Main advantage | Main danger |
|---|---|---|---|
| Exact scan | Candidate corpus is manageable; score is arbitrary | Exact for the actual score | Linear cost |
| Two-stage symmetric surrogate + directed rerank | A sound candidate generator exists | Fast and semantically faithful final ranking | Candidate-generation recall can miss directional optima |
| MIPS / asymmetric embedding | \(C(q,x)=\phi_Q(q)^\top\phi_D(x)\) or reducible to it | Uses mature IP ANN machinery | Reduction may alter score meaning or hurt graph/quantization behavior |
| Directed graph / custom ANN | Direction itself is the retrieval topology | Can preserve asymmetric semantics | Less standardized theory and implementation maturity |
| Learned retrieval index | Training data defines relevance more reliably than a hand-built geometry | Optimizes end task | Can drift, become opaque, or need extensive monitoring |

### Recommended Nexus default

For cross-label compatibility, Nexus should use **separate query and candidate roles**:

```text
QueryRole = source-label schema + query transform
CandidateRole = target-label schema + candidate transform
Score = declared directional compatibility
```

Then choose one of three modes:

1. **Exact directional rank**
   Use brute-force/vectorized scoring when corpus size or latency permits. This is the canonical correctness oracle.

2. **Metric candidate generation + exact directional rerank**
   Build an ANN index only over a separately justified symmetric embedding. Retrieve \(R\gg k\) candidates, then compute exact \(C(q,x)\) and return the top \(k\). Report end-to-end recall versus exact directional top-\(k\).

3. **Native MIPS/asymmetric ANN**
   Only when \(C\) has an explicit factorization or tested reduction into a supported MIPS/asymmetric contract.

A standard single-space HNSW index should not be used merely because \(C\) returns numbers.

***

## Quasimetric versus arbitrary directional score

A directed score \(d(x,y)\) is a quasimetric only if its actual axioms have been established. A common definition requires:

\[
d(x,x)=0,
\]

\[
d(x,z)\le d(x,y)+d(y,z),
\]

with asymmetry permitted:

\[
d(x,y)\ne d(y,x).
\]

Some formulations also require separation in one or both directions. Nexus should record the exact adopted definition, rather than rely on a label.

A directional compatibility score such as

\[
C_W(H,K)
=
\sum_{\ell,m} w_{\ell m}
\langle P_{\ell\to m}H_\ell,K_m\rangle
\]

does not automatically become a quasimetric under the transformation

\[
d(H,K)=a-C_W(H,K).
\]

It may be negative, unbounded, nonzero on self pairs, undefined across roles, or violate every directed triangle relation.

***

## Divergences such as KL

KL divergence,

\[
D_{\mathrm{KL}}(p\|q)
=
\sum_i p_i\log\frac{p_i}{q_i},
\]

is nonnegative and zero only when \(p=q\) under its usual domain conditions, but it is asymmetric and lacks ordinary triangle inequality.

Nexus options for KL-like scoring:

- exact scan;
- use a task-appropriate symmetric surrogate, such as Jensen–Shannon divergence, only if semantics permit the symmetrization;
- use a specialized divergence index with its own assumptions;
- learn dual embeddings and validate that the candidate-generation embedding preserves target recall;
- use a Bregman-divergence method where its specific assumptions hold.

Do not silently symmetrize

\[
D_{\mathrm{KL}}(p\|q)
\mapsto
\frac12[D_{\mathrm{KL}}(p\|q)+D_{\mathrm{KL}}(q\|p)]
\]

if direction encodes the purpose of the retrieval. Symmetrization can erase the difference between “how well evidence explains a hypothesis” and “how well a hypothesis predicts evidence.”

***

# 7. HNSW failure modes for nonmetric scores

## What can go wrong

The following are **empirical/structural risks**, not universal theorems that every nonmetric score fails.

| Failure mode | Mechanism | Why geometry matters |
|---|---|---|
| Local minima | Greedy traversal arrives at a node whose neighbors all score worse despite a better distant node | Local score order does not correlate with global progress |
| Weak navigability | Local neighbor edges do not create effective paths toward query-optimal regions | Score neighborhoods lack coherent multi-scale structure |
| Hub formation | Many points regard a few high-score items as neighbors | Unbounded popularity/magnitude or directional asymmetry distorts graph degree |
| Insertion-order sensitivity | Early local links consume bounded degree and suppress later useful links | Noncoherent neighborhoods make pruning choices brittle |
| Disconnected useful neighborhoods | Candidate graph omits bridges needed for certain query directions | Candidate-to-candidate score differs from query-to-candidate score |
| Poor directed recall | Undirected graph edge construction does not match directional objective | \(C(q,x)\) is not represented by \(C(x_i,x_j)\) |
| Quantization distortion | Compression errors reorder scores | Margin between candidates is small or score is sensitive/non-Lipschitz |
| Metric-pruning invalidity | A lower bound assumed from triangle inequality is false | Exactness/recall guarantee becomes unsound |
| Normalization mismatch | Query and index use different transforms or norm conventions | They no longer occupy the same declared geometry |

## An explicit greedy-traversal pathology

Consider a graph with entry node \(e\), local nodes \(a,b\), and a target-optimal node \(t\). Suppose lower score is better for query \(q\):

\[
d(q,e)=10,\quad d(q,a)=9,\quad d(q,b)=8,\quad d(q,t)=0.
\]

Edges are:

\[
e\leftrightarrow a,\qquad a\leftrightarrow b,\qquad t\leftrightarrow b
\]

but assume construction/pruning removes \(b\leftrightarrow t\), leaving \(t\) reachable only through a graph region that greedy search does not expand at its chosen beam. Or more severely, the graph has a local basin where all exposed neighbors of \(b\) have query score worse than \(8\), while the true top candidate lies behind a temporarily worse step.

A pure greedy traversal stops at \(b\), even though \(t\) is globally optimal. This can happen in metric spaces too—HNSW is approximate—but coherent metric neighborhoods and wider beam exploration reduce the likelihood. An arbitrary score can make such basins systematic rather than exceptional.

The correct control is not a claim that triangle inequality eliminates all traps. It is:

- adequate `ef_construction`,
- adequate `ef_search`,
- construction diagnostics,
- exact-baseline recall measurement,
- multiple entry points or fallback strategies where needed,
- and a retrieval geometry whose local score structure matches the task.

## Legal index selection

Legal:

- HNSW;
- DiskANN-style graph ANN;
- IVF/PQ;
- metric trees where dimensionality and workload justify them;
- exact scan.

Preferred:

- HNSW or DiskANN for high-recall graph ANN;
- IVF/PQ where memory/scale dominates;
- exact scan as benchmark oracle and for smaller filtered candidate sets.

### `PSD_KERNEL_PSEUDOMETRIC`

Legal only after an explicit feature representation or valid distance construction.

Required:

- document null-space equivalence;
- bind kernel/feature-map version;
- specify whether equal-distance states are deduplicated, tied, or retained as distinct records.

### `MIPS_INNER_PRODUCT` and `FACTORIZED_BILINEAR_MIPS`

Legal:

- direct inner-product HNSW/IVF implementations;
- MIPS-specific approaches;
- asymmetric transform methods;
- exact scan.

Not legal:

- metric-tree claims or triangle-based pruning unless a particular transformed metric construction is established and the deployed index actually uses it.

### `QUASIMETRIC_DIRECTED`

Legal only after proof or explicit construction of a directed triangle relation, plus an index whose assumptions match it.

Default until then:

- exact scan;
- or metric candidate generation plus exact directed rerank.

### `GENERAL_SCORE_EXACT_ONLY`

Legal:

- exact scan;
- cached exact score tables where finite;
- domain-specific learned/routing approaches with a separately validated contract.

Prohibited:

- “HNSW because it takes a callback” as a canonical default.

# 10. Aligned-label HTLA recommendation

Your existing HTLA document already identifies the correct strong case:

\[
B_w(H,K)
=
\sum_{\ell}w_\ell\langle H_\ell,K_\ell\rangle,
\qquad w_\ell>0.
\]

With every weight strictly positive, this is an inner product and induces

\[
\|H\|_w=\sqrt{B_w(H,H)}.
\]

That directly supports a standard Euclidean geometry after diagonal weighting, as well as normalized angular/chordal geometry for cosine-like retrieval. The HTLA paper correctly distinguishes this aligned-label construction from directed cross-label compatibility and states that an asymmetric or indefinite \(A\) must not inherit inner-product or metric terminology. ## Canonical aligned-label contract

For ordinary HVD “find states similar to this state” retrieval:

```text
Geometry: ANGULAR_METRIC or WEIGHTED_EUCLIDEAN_METRIC
Representation:
  z(H) = diag(sqrt(w_l)) · flat(H)
Score:
  cosine(z(q), z(x)) for user-facing graded similarity
Index:
  normalized inner-product HNSW or L2 HNSW
Formal metric:
  angular distance or chordal Euclidean distance
```

This is the strongest, simplest, and most auditable default.

### Why not make \(1-\cos\) canonical?

It preserves the desired ranking, but it is not a metric. There is no reason to make the nonmetric transform the formal semantic geometry when angular and chordal metrics provide the same top-\(k\) order after normalization.

Use \(1-\cos\) only as an implementation score or reporting convention if needed; label it `COSINE_DISSIMILARITY_NONMETRIC`.

# 11. HTNLA consequences

## A learned transform changes the geometry

If

\[
y=F_g(x)
\]

is an HTNLA representation under model generation \(g\), retrieval does not occur in raw state space anymore. It occurs under the pullback score:

\[
d_g(x,x')
=
d_{\mathrm{index}}(F_g(x),F_g(x')).
\]

When \(g\) changes to \(g+1\), the retrieval geometry may change even if:

- dimensions remain identical;
- vectors remain finite;
- the same HNSW parameter settings are used;
- the model change appears numerically small.

The HTNLA source document already identifies the key invariant: a query transformed under one representation generation should not be searched against an index built from another incompatible generation. The document explicitly states that a model change may require rebuilding, dual-generation serving, migration/re-encoding, a compatibility bridge, or fail-closed rejection. ## Geometry staleness

An index is geometrically stale if any element changes that can alter top-\(k\) ordering:

- HTNLA weights;
- activation behavior;
- k-WTA rule or tie-breaking;
- output normalization;
- label schema;
- weighted inner product;
- cross-label transforms \(P_{\ell\to m}\);
- score operator \(A\);
- cosine versus dot-product selection;
- quantization codebook;
- score implementation precision or hardware kernel where reproducibility matters.

### Approximate projections

If a projection \(P\) preserves pairwise Euclidean distances on a declared finite corpus:

\[
(1-\varepsilon)\|x-y\|_2^2
\le
\|Px-Py\|_2^2
\le
(1+\varepsilon)\|x-y\|_2^2,
\]

then it preserves distance approximately on that finite set. It does **not** guarantee every nearest-neighbor rank is unchanged.

A top-\(k\) ordering is stable only when score/distance gaps exceed the approximation error. For a nearest neighbor \(x_1\) and runner-up \(x_2\), a sufficient style of condition is that the margin

\[
d(q,x_2)-d(q,x_1)
\]

be larger than the worst-case distortion in comparing those candidates. In dense high-dimensional data, near ties can be common; distance preservation therefore does not imply rank preservation.

The existing HTLA material correctly scopes Johnson–Lindenstrauss guarantees to finite-set pairwise distortion, not semantic preservation, invertibility, identity preservation, or universal exact ranking. # 12. Validation specification

## Three layers of validation

Nexus should explicitly distinguish **proof**, **numerical checking**, and **retrieval measurement**.

| Layer | What it can establish | What it cannot establish |
|---|---|---|
| Construction/theorem | A property for all states in the declared mathematical domain, under theorem assumptions | Real workload relevance, hardware performance, learned-model generalization |
| Numerical validation | Detect obvious implementation/configuration defects; estimate conditioning and violations | Prove universal PSD, metricity, or triangle inequality from finite samples |
| Empirical benchmark | Recall, latency, stability, and robustness over declared datasets/workloads | Prove formal correctness outside tested distributions |

## A. Construction/proof tests

These should be required wherever Nexus claims a mathematical geometry.

### Weighted aligned metric

Verify by construction:

```text
- Every label has declared dimension and coordinate semantics.
- All weights satisfy w_l > 0.
- Weighted flattening uses sqrt(w_l) exactly.
- Same normalization is used for insertion and query.
- Zero-norm handling is declared.
```

Then the metric claim follows mathematically.

### Mahalanobis metric

Require:

```text
- A = A^T within declared exact/numerical representation.
- A is positive definite on the declared domain.
- A = L^T L is constructed or numerically certified.
- Index vectors are Lx, and queries use the identical L.
```

### PSD kernel / pseudometric

Require:

```text
- Symmetry proof or construction.
- A PSD factorization A = B^T B, or a theorem establishing PSD.
- Explicit null-space/equivalence policy.
```

### MIPS

Require:

```text
- Exact objective: argmax q^T x or argmax phi_Q(q)^T phi_D(x).
- Query and database transforms fixed and versioned.
- Normalization policy states whether magnitude is intentionally preserved.
```

### Directed quasimetric

Require an actual proof of the adopted axiom set, including:

```text
d(x, x) = 0
d(x, z) <= d(x, y) + d(y, z)
declared separation condition
explicit domain of x and y
```

Without this proof, the contract is `DIRECTED_COMPATIBILITY`, not `QUASIMETRIC`.

***

## B. Numerical property tests

These are valuable **falsification tests**, not proofs.

### Universal safety tests

```text
finite_score_rate
nan_rate
positive_infinity_rate
negative_infinity_rate
determinism_under_repeated_evaluation
tie_rate
score_range
self_score_distribution
query/candidate schema validation
representation-generation compatibility
```

### Symmetry diagnostics

For a score intended to be symmetric:

\[
\Delta_{\text{sym}}(x,y)
=
|s(x,y)-s(y,x)|.
\]

Record:

```text
max_symmetry_error
median_symmetry_error
p99_symmetry_error
relative_symmetry_error
```

For a directional score, record **asymmetry intentionally**:

\[
A_{\text{dir}}(x,y)
=
C(x,y)-C(y,x).
\]

Do not treat directionality as a numerical defect if it is semantic.

### Triangle diagnostics

For a purported distance \(d\), sample triples \((x,y,z)\) and calculate

\[
v(x,y,z)
=
d(x,z)-d(x,y)-d(y,z).
\]

Record:

```text
triangle_violation_rate = Pr[v > tolerance]
max_absolute_violation
p99_violation
maximum_observed_relaxed_constant
```

For nonnegative denominators, estimate:

\[
\hat c
=
\max_{\text{sampled triples}}
\frac{d(x,z)}
{d(x,y)+d(y,z)+\epsilon}.
\]

Interpretation:

- \(\hat c\le1+\delta\) on a sample is evidence against gross violation.
- It is **not** a proof that \(d\) is a metric or a \(c\)-quasimetric universally.
- A high violation rate is a strong warning against metric-index claims.

### PSD diagnostics

For sampled states \(x_1,\dots,x_n\), form the Gram matrix:

\[
G_{ij}=K(x_i,x_j).
\]

Check:

```text
symmetrization error ||G-G^T||
minimum eigenvalue
negative eigenvalue mass
condition number
rank estimate
Cholesky success/failure
```

Interpretation:

- A significantly negative eigenvalue falsifies PSD for that sample/kernel evaluation.
- Nonnegative eigenvalues for one finite sample do not prove global PSD.
- For a fixed finite deployed catalog, PSD of that catalog’s Gram matrix may be operationally sufficient for a finite-kernel method—but it still does not define behavior for future inputs.

### Directional score diagnostics

```text
- Query-to-candidate score distribution
- Candidate-to-candidate score distribution
- Correlation between candidate graph proximity and query ranking
- Direction reversal sensitivity
- Fraction of undefined candidate-candidate comparisons
- In/out-degree distribution in any directed graph
- Hubness measures
```

These directly test whether an HNSW-like graph’s construction relation resembles its serving relation.

## C. Retrieval benchmark requirements

Every ANN geometry contract should have an exact baseline over a frozen corpus/query set.

### Core metrics

```text
Recall@k
Recall@R for reranking candidate pool R
MRR / nDCG where task labels exist
exact-score regret:
  score(q, exact_top_1) - score(q, ann_top_1)
top-k overlap
p50/p95/p99 latency
throughput
build time
memory/vector
index size
insertion-order variance
query-order variance
failure rate
```

### Directional compatibility benchmark

For each query \(q\):

1. Compute exact top-\(k\) under the production score \(C(q,x)\).
2. Run candidate generation.
3. Rerank candidates with exact \(C(q,x)\).
4. Measure whether the true directed top-\(k\) appears in the candidate pool and final returned list.

Two distinct recall measures are necessary:

\[
\mathrm{CandidateRecall@R}
=
\frac{
|\operatorname{TopK}_{C}(q)
\cap
\operatorname{Candidates}_{R}(q)|
}{k},
\]

and

\[
\mathrm{EndToEndRecall@k}
=
\frac{
|\operatorname{TopK}_{C}(q)
\cap
\operatorname{ReturnedTopK}(q)|
}{k}.
\]

A high reranker quality cannot repair a candidate generator that never retrieves the true answer.

### Stress suites

Benchmark under:

- random queries;
- high-norm and low-norm queries;
- sparse/dense label compositions;
- each source/target label pair;
- rare and dense clusters;
- near-duplicate states;
- adversarially asymmetric query/candidate examples;
- transformed states around HTNLA support changes;
- representative filters and post-filtering;
- generation transitions;
- quantized versus unquantized storage;
- multiple insertion orders.

# 13. Triangle-property recommendation

## Nexus should not impose one global triangle law

A universal requirement that all Nexus retrieval scores be metrics would be too restrictive and would erase legitimate MIPS and directional compatibility tasks.

A universal rule that no triangle property matters would be unsafe and would make it easy to misapply metric indexes, claim invalid guarantees, and deploy brittle graph retrieval.

### Recommended policy by class

| Nexus retrieval class | Triangle requirement | Reason |
|---|---|---|
| Ordinary same-space similarity retrieval | **Require a true metric or a provably ranking-equivalent implementation representation** | Stable canonical geometry, broad index compatibility, clear semantics |
| Angular/cosine-like retrieval | Require angular or chordal metric as formal geometry; permit normalized IP implementation | Same ranking, clean metric semantics |
| Pseudometric retrieval | Require pseudometric construction and explicit quotient policy | Zero distance is intentional representational collapse |
| Metric-tree or triangle-pruned retrieval | Require ordinary triangle inequality on deployed distance | Sound pruning depends on it |
| Metric-spanner/certified exactness extensions | Require ordinary triangle inequality or a theorem-supported equivalent | Bounds depend on it |
| MIPS | Do not require triangle inequality | Objective is ranking by inner product; use MIPS contract |
| Asymmetric/quasimetric retrieval | Require directed triangle inequality only if claiming quasimetric methods/guarantees | Direction alone is insufficient |
| General directional compatibility | No triangle requirement, but no metric claims and no default HNSW | Exact or surrogate+rerank with measured recall |
| Learned retrieval | No inherent triangle requirement | Contract is empirical relevance plus versioned encoders/index |

### Canonical recommendation

> **Nexus should canonically require ordinary metric geometry for “ordinary HVD similarity retrieval,” not for every retrieval problem.**

For all other score families, Nexus should require a declared alternative contract and forbid accidental metric terminology.

# 14. Proposed Nexus engineering laws

## Candidate laws for the canonical monograph

1. **Geometry declaration law**
   Every ANN-backed retrieval field SHALL declare a `RetrievalGeometry` class, score direction, query/candidate schemas, normalization policy, and representation generation.

2. **No arbitrary-score HNSW law**
   A callable score alone SHALL NOT authorize construction of an HNSW, IVF, DiskANN, metric-tree, or other ANN index.

3. **Metric terminology law**
   A score SHALL NOT be called a distance, metric, cosine, kernel metric, or quasimetric unless its required mathematical properties are established for the declared domain.

4. **Aligned-label geometry law**
   HTLA aligned-label weighted similarity with strictly positive weights SHALL be represented as a weighted inner-product geometry and SHALL expose either Euclidean/chordal or angular metric semantics for ANN.

5. **PSD law**
   A symmetric PSD operator MAY define a kernel or pseudometric after a declared construction. It SHALL NOT be advertised as a strict metric without an injectivity/separation argument.

6. **Indefinite-form law**
   An indefinite bilinear form SHALL be typed as a compatibility score, not an inner product, norm, cosine, or distance.

7. **Directionality law**
   An asymmetric cross-label score SHALL NOT be typed as a quasimetric merely because it is directional. A directed triangle contract must be separately established.

8. **MIPS separation law**
   Maximum-inner-product and factorized bilinear retrieval SHALL be typed separately from metric nearest-neighbor retrieval, even when they share a physical ANN implementation.

9. **Candidate/rerank law**
   A directional or general compatibility score used with a metric ANN candidate generator SHALL be reranked by the exact production score before final output unless an equivalence proof exists.

10. **Exact-oracle law**
    Every approximate retrieval configuration SHALL have a reproducible exact-ranking oracle for its declared production score and a versioned benchmark suite.

11. **Generation-binding law**
    An ANN index SHALL bind to representation generation, transform generation, geometry contract version, score version, normalization version, and quantization version.

12. **Stale-index law**
    A query representation generation incompatible with the indexed generation SHALL trigger rebuild, dual serving, a validated bridge, or fail-closed rejection.

13. **No semantic promotion law**
    Similarity, compatibility, ANN rank, kernel proximity, and approximate recall SHALL NOT be promoted to identity, truth, authorization, continuity, or canonical state.

14. **Guarantee-scope law**
    A metric theorem, empirical benchmark, implementation capability, and Nexus preference SHALL be labeled separately and SHALL NOT substitute for one another.

# 15. Adversarial review

## Strongest case against a conservative geometry policy

The strongest contrary position is substantial:

1. **HNSW is already used for nonmetric inner product and cosine-like search.**
   Major systems expose HNSW with inner product, cosine, and \(L_2\) objectives. FAISS directly supports inner product and documents its relationship to cosine and \(L_2\); OpenSearch exposes HNSW with \(L_2\), cosine, and inner-product spaces across several engines. [github](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)

2. **Triangle inequality is not invoked by standard HNSW’s core traversal.**
   The algorithm directly evaluates scores and uses bounded graph exploration. A strict metric proof is therefore not necessary for it to return useful results.

3. **PSD is unnecessarily restrictive for retrieval.**
   Many useful learned relevance models, attention-like compatibility functions, cross-encoders, and task-specific bilinear scores are asymmetric or indefinite. Forcing them into a PSD kernel can discard predictive information.

4. **Symmetrization can destroy meaning.**
   Evidence \(\rightarrow\) hypothesis and hypothesis \(\rightarrow\) evidence can encode genuinely different questions. Replacing directional compatibility with a symmetric distance may change the task rather than merely regularize it.

5. **MIPS transformations can distort engineering behavior.**
   Even algebraically correct transformations can alter distribution, norms, quantization behavior, and graph construction quality. FAISS explicitly cautions that an inner-product-to-\(L_2\) reduction may not interact well with quantization and other index structures. [github](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)

6. **Empirical recall may be enough in a production system.**
   If the corpus, query distribution, score version, and SLO are finite and controlled, a measured recall/latency contract against exact ranking might matter more than a universal metric proof.

## Nexus response

Nexus should accept that case—but not draw the unsafe conclusion.

The right conclusion is:

- **Do not require a metric where the task is intrinsically MIPS or directional compatibility.**
- **Do require that the task be named correctly, indexed through a matching method, and continuously measured against exact ranking.**
- **Do not call a nonmetric or directional score a distance merely to obtain a familiar ANN implementation.**
- **Do not let undocumented score changes silently alter graph geometry.**

Thus, for nonmetric scoring, empirical recall can be operationally sufficient **only when all of the following are true**:

1. The production score is explicit and versioned.
2. Exact baseline ranking is feasible offline on a representative benchmark.
3. Recall/latency targets are explicitly accepted as an approximation contract.
4. Candidate-generation and final-rerank recall are measured separately.

**HNSW does not formally require the triangle inequality.** The statement “HNSW depends on the triangle inequality” is **FALSE** as a strict algorithmic or implementation requirement, **PARTIALLY TRUE** only in the limited sense that metric structure (including triangle inequality) can improve navigability heuristics, pruning power in related analyses, and empirical reliability on some data distributions, and **CONTEXT-DEPENDENT** for theoretical guarantees or exactness claims.

### A. Executive Conclusion

1. **Does HNSW require triangle inequality?** No. The core algorithm (incremental hierarchical proximity-graph construction + greedy/beam search) executes with any callable dissimilarity or similarity that produces comparable scores. Implementations (hnswlib, FAISS, NMSLIB) accept L2, inner product, cosine (via \(1-\cos\)), and custom distances, including non-metrics.

2. **What it actually requires (execution / implementation):** A total order on candidate scores (smaller-is-better distance or larger-is-better similarity after conversion), finite comparable values, and the ability to evaluate the score between any pair. Symmetry is convenient but not mandatory; asymmetry is supported by treating the graph as directed or by separate left/right query handling (NMSLIB). Identity of indiscernibles is not required.

3. **What materially improves behavior:** Local connectivity that approximates a navigable small-world / relative-neighborhood structure; diversity heuristics during neighbor selection; moderate intrinsic dimensionality or bounded expansion that limits hubness; and (empirically) scores that are at least roughly continuous and non-pathological. Triangle inequality helps some diversification/pruning analyses and can reduce pathological local minima, but is neither necessary nor always sufficient.

4. **Ordinary HVD similarity retrieval (aligned-label HTLA):** Prefer a true metric or strong pseudometric induced by a strictly positive weighted inner product (or cosine / angular after normalization). This is the safest default for HNSW and gives the strongest empirical and analytical support.

5. **Asymmetric cross-label compatibility:** Treat as a distinct class (directed score / MIPS / general ranking). Do **not** silently feed it to a symmetric HNSW index. Prefer explicit MIPS reductions, directed/bipartite graphs, separate query/database transforms, or exact scan + ranking when uniqueness or directional semantics matter. Symmetrization often degrades semantics and recall.

**Nexus design preference (not a theorem):** Declare the retrieval geometry explicitly, bind index generation to representation/geometry generation, and validate recall against an exact baseline. Arbitrary scores must not back an HNSW index without that contract.

### B. Mathematical Taxonomy

- **Metric**: \(d(x,y)\ge0\), \(d(x,y)=0\Leftrightarrow x=y\), symmetry, triangle inequality.
- **Pseudometric**: Allows \(d(x,y)=0\) for \(x\neq y\).
- **Semimetric**: Terminology varies; often means symmetry + non-negativity without triangle inequality (or vice versa). Avoid assuming a universal definition.
- **Quasimetric / quasi-metric**: Asymmetric, usually with a directed triangle inequality \(d(x,z)\le d(x,y)+d(y,z)\).
- **Similarity**: Larger-is-better score; may or may not induce a distance via a monotone transform.
- **PSD kernel**: Symmetric positive-semidefinite \(K\) corresponding to an inner product in a feature space (by Moore–Aronszajn). Induces a pseudometric via \(d^2(x,y)=K(x,x)+K(y,y)-2K(x,y)\).
- **Indefinite kernel / bilinear form**: Eigenvalues of both signs; no Hilbert-space geometry, cosine normalization can be meaningless or unstable.
- **Divergence** (e.g., KL): Typically asymmetric, non-negative when defined, no triangle inequality; nearest-neighbor search is still well-defined as ranking.
- **MIPS**: Maximize \(x^\top y\) (or \(x^\top A y\)); not a metric.
- **General ranking score**: Any total order; only the ranking matters for top-\(k\).

Aligned HTLA weighted inner product with \(w_\ell>0\) yields a true inner-product geometry and therefore a metric after the usual constructions (Euclidean, angular, etc.). Cross-label \(C_W\) with arbitrary \(A_W\) can fall into any of the classes above depending on symmetry and definiteness of \(A_W\).

### C. HNSW Requirements (Theorem / Implementation / Empirical)

**Original paper (Malkov & Yashunin, arXiv:1603.09320):** Presents HNSW as a “general metric space search index.” Performance claims and some heuristics are framed in metric language.

**Algorithm itself:** Builds a multi-layer proximity graph by inserting points, finding approximate neighbors via greedy/beam search, and applying a diversification heuristic (relative-neighborhood style). Search is the same greedy descent from the top layer. No step *executes* a triangle-inequality test. The algorithm only needs a score function that ranks candidates.

**Implementations:**
- hnswlib: L2, inner product (`1 - x·y`), cosine (`1 - cos`). Explicitly notes that inner product is *not* a metric (“an element can be closer to some other element than to itself”).
- FAISS / NMSLIB: Support the same families plus custom and non-metric distances. NMSLIB was explicitly built for non-metric spaces and includes HNSW as a strong method.

**Empirical / theoretical follow-on:**
- Boytsov & Nyberg (SISAP 2019 / arXiv:1910.03534) show that neighborhood-graph search (SW-graph / HNSW family) works *directly* on challenging non-metric and substantially non-symmetric distances (KL, Itakura–Saito, Rényi, BM25, etc.) without metrization or full symmetrization. Full filter-and-refine symmetrization is often *worse*; building the graph with a modified (e.g., symmetrized) distance can help, but the original non-metric score can still yield high recall and large speed-ups.
- Triangle inequality is used in *some* exactness or pruning analyses (spanners, metric-bound verification) and in classical metric trees, but graph ANN does not rely on it for correctness of the approximate procedure.

**Classification of “HNSW depends on the triangle inequality”:** FALSE as a hard requirement; the algorithm runs and can achieve high recall without it. Metric structure is a helpful *heuristic* and can improve theoretical analyses or reduce certain failure modes (hubs, local minima), but is not necessary.

### D. HTLA Aligned-Label Retrieval

Strongest appropriate geometry: the weighted inner-product geometry
\[
B_w(H,K)=\sum_\ell w_\ell\langle H_\ell,K_\ell\rangle,\qquad w_\ell>0.
\]
This is an inner product, induces a norm, and yields a true metric (Euclidean after flattening, or angular/cosine after normalization). Cosine similarity itself is not a metric; \(1-\cos\) violates the triangle inequality; angular distance \(\arccos(\cos)\) is a metric on the sphere.

Practical recommendation: normalize (or use angular / Euclidean) and declare the geometry as `ANGULAR_METRIC` or `EUCLIDEAN_METRIC`. HNSW is then on its strongest empirical footing.

### E. HTLA Cross-Label Retrieval

- If \(A_W\) is symmetric positive-definite → true inner-product geometry (treat as aligned case).
- Symmetric positive-semidefinite → kernel / pseudometric geometry; HNSW still usable, but identity of indiscernibles may fail.
- Indefinite → no Hilbert geometry; treat as general score or MIPS-like; HNSW may still rank but guarantees and heuristics degrade.
- Asymmetric → directed score / quasimetric (if directed triangle holds) or pure ranking. Do not feed to a symmetric HNSW without an explicit reduction or directed index.

MIPS reductions (asymmetric transforms that embed into Euclidean or cosine space) exist and are widely used, but they can distort topology and are not free. Direct graph construction on the original score is often preferable when the score is the true objective.

### F. HTNLA Retrieval

Nonlinear / learned maps change the geometry. A model-generation change (\(\theta_g\to\theta_{g+1}\)) can invalidate an index built under the old representation even if every individual vector remains numerically valid. The Nexus invariant already stated in the source papers is required:

```text
representation_generation(query) must be compatible with representation_generation(index)
```

Approximation (projection, quantization, low-rank) further relaxes distance preservation; nearest-neighbor rankings are only approximately preserved under JL-type or other distortion bounds on a finite set. Geometry-contract versioning should be part of index metadata.

### H. Triangle-Property Recommendation

- **Ordinary aligned HVD retrieval:** Prefer a true metric (or strong pseudometric). Triangle inequality is desirable but not mandatory for HNSW.
- **Cross-label / asymmetric:** Do **not** require ordinary triangle inequality. If a directed triangle holds, a quasimetric analysis may help; otherwise treat as ranking/MIPS.
- **No global Nexus mandate** that every score must satisfy triangle inequality. Require only that the declared geometry class matches the index family and that empirical recall is validated.

Relaxed triangle inequalities (\(d(x,z)\le c[d(x,y)+d(y,z)]\)) appear in some ANN literature; they preserve some pruning power but are not a core HNSW requirement.

### I. Validation Specification

**Construction / theorem guarantees** (when claimed):
- Explicit proof or citation that the score is a metric / PSD kernel / etc.

**Numerical validation (sampled states):**
- Finite, non-NaN outputs.
- Symmetry error \(\max |C(H,K)-C(K,H)|\).
- Empirical triangle-violation rate (or directed version).
- Eigenvalue test for PSD claim (on the effective Gram or operator matrix).
- Identity behavior (self-score extremal).

A finite sample never *proves* a universal metric property; it only detects obvious failures.

**Empirical retrieval benchmark (mandatory for production):**
- Exact baseline (brute-force or verified exact index) on a held-out query set.
- Recall@\(k\), latency, and stability under insertion order / model generation.
- For generation changes: dual-index or rebuild + recall delta.

### J. Proposed Nexus Engineering Laws

1. Undeclared geometry must not back an ANN/HNSW index.
2. Arbitrary compatibility scores must not be advertised as distances or metrics.
3. ANN index generation must bind to representation generation *and* geometry generation.
4. Metric-required algorithms (certain trees, exact pruning) require a verified metric contract; HNSW does not.
5. Asymmetric or directional scores require an explicit directed, MIPS, or ranking contract; silent symmetrization is forbidden when semantics matter.
6. Empirical recall against an exact baseline is required before an index is declared production-ready; high recall does not become a formal correctness guarantee.
7. Similarity / ANN rank never becomes identity, truth, authorization, or continuity.

### K. Open Research Questions

- Precise quantitative relationship between degree of triangle violation (or asymmetry) and HNSW navigability / hub formation on the specific label geometries that arise in HTLA/HTNLA.
- Optimal index-construction proxy distances for a given query-time asymmetric score (Boytsov & Nyberg observation).
- When a learned HTNLA transform preserves enough local geometry that an old index remains usable under a controlled distortion budget.

- Tight characterizations of when MIPS reductions preserve the ranking that HTLA/HTNLA actually intends.

### Adversarial Review (Strongest Opposing Case)

Counter-evidence is real and must be acknowledged:

- HNSW and related neighborhood graphs achieve high recall and large speed-ups on strongly non-metric and non-symmetric distances (KL family, BM25, etc.) without any triangle inequality.
- Production libraries treat inner product and \(1-\cos\) as first-class citizens even though they are not metrics.
- Forcing a metric embedding or symmetrization frequently *degrades* both semantics and measured recall.
- For many practical embedding spaces the dominant failure modes are hubness and high intrinsic dimensionality, not pure triangle violation.
- Empirical recall testing on representative workloads can be operationally sufficient even when a formal metric proof is unavailable.

**What Nexus should do anyway:** Adopt the typed geometry contract, require generation binding, and demand exact-baseline recall validation. The cost of an undeclared arbitrary score silently driving an HNSW index (silent ranking instability, generation mismatch, or loss of directional meaning) is higher than the cost of the modest type discipline. The middle path is exactly the one argued above: HNSW does not need a metric, but geometry still matters, and the architecture must make the geometry explicit rather than hope.

This contract is strong enough to rewrite the Nexus technical specification without either of the two errors named in the prompt.

# Retrieval Geometry for Nexus 4: A Canonical Contract for HTLA/HTNLA Similarity and ANN/HNSW Search

## Executive conclusion

The attached Nexus research brief is treated as the authoritative specification of the research problem: the question is not merely whether a score is callable by HNSW, but what mathematical contract should sit between HTLA/HTNLA semantics, HVD retrieval geometry, and a concrete ANN index. fileciteturn0file0

The central conclusion is a defensible middle between the two failure modes identified in the brief:

> **HNSW does not require a metric or the triangle inequality in order to execute, and neither the original HNSW evidence nor major implementations impose that requirement. But “any callable score is safe” is also wrong. HNSW relies on the existence of a useful, navigable neighborhood graph, and its construction heuristics make pairwise geometric comparisons whose quality can deteriorate when the score has incoherent neighborhood structure.**

There is an additional architectural point that is especially important for Nexus: **raw triangle inequality is too strong and often the wrong admission test for HNSW.** Standard top-\(k\) HNSW is fundamentally comparison-based. If its dissimilarity is replaced everywhere by a strictly increasing transform, its order comparisons—and therefore, absent ties/numerical effects, its graph construction and search decisions—are preserved. Consequently, a nonmetric quantity can be *ordinally equivalent* to a metric and be just as suitable for HNSW. Squared Euclidean distance is the simplest example: hnswlib calls \(\sum_i(x_i-y_i)^2\) its L2 distance even though squared Euclidean distance fails the ordinary triangle inequality; it induces exactly the same ordering as Euclidean distance. hnswlib likewise implements \(1-\cos(x,y)\), another nonmetric raw dissimilarity, while Faiss explicitly notes its monotone relationship to Euclidean distance on normalized vectors. citeturn21view0turn22view2

This suggests a Nexus concept that is more useful than a binary `METRIC/NONMETRIC` flag:

\[
\boxed{\text{METRIC\_RANKING / ORDINAL\_METRIC}}
\]

meaning that the supplied score is known to be a strictly monotone transform of a genuine metric, even if the numerical function itself does not satisfy the metric axioms.

### Research method

Priority was given to the original HNSW paper, peer-reviewed or archival ANN/MIPS work, recent graph-ANN theory, and authoritative implementation documentation. The original HNSW paper is particularly important because it does something often omitted in secondary descriptions: it explicitly includes a section on “general spaces,” meaning spaces that can be nonsymmetric or violate triangle inequality, and reports HNSW experiments on such data. citeturn5view0turn5view1turn5view2

Modern theory was then used to separate what the original empirical success does **not** prove. Indyk and Xu's NeurIPS 2023 analysis gives worst-case instances on which HNSW needs empirically linear-in-\(n\) work to reach reasonable accuracy, while 2025 work on adaptive beam search proves approximation when the underlying search graph satisfies a navigability property. These results make “navigability” a more precise theoretical concept than “the score satisfies triangle inequality.” citeturn24view0turn24view1

Implementation claims were checked against current hnswlib, NMSLIB, Faiss, pgvector, and Lucene documentation. hnswlib 0.9.0 supports squared L2, \(1-\)inner product, and cosine distance and explicitly says inner product is not a metric; its C++ API permits user-defined distances. NMSLIB describes itself as a toolkit for generic and nonmetric spaces. pgvector exposes HNSW indexes for L2, inner product, cosine, L1, Hamming, and Jaccard, while current Lucene exposes Euclidean, dot-product, cosine, and maximum-inner-product vector similarity modes. citeturn21view0turn15search4turn22view3turn23search0

## Mathematical taxonomy and canonical transformations

A safe Nexus API should avoid treating all pairwise real-valued functions as variants of the same concept.

| Structure | Core mathematical contract | What it gives Nexus | What it does **not** automatically give |
|---|---|---|---|
| **Metric** | \(d\ge0\); \(d(x,y)=0\iff x=y\); symmetry; ordinary triangle | Genuine nearest-neighbor geometry; metric pruning available | Low dimension, easy ANN, or good HNSW recall |
| **Pseudometric** | Metric axioms except distinct objects may have \(d=0\) | Metric geometry on equivalence classes | Object identity |
| **Semimetric** | Terminology varies; often symmetric and separating but without triangle | Potential ranking geometry | A stable portable contract unless axioms are spelled out |
| **Directed quasimetric** | Typically \(d(x,x)=0\), nonnegative, directed triangle, but not symmetry | Principled asymmetric distance geometry | Compatibility of standard undirected/bidirectional ANN heuristics |
| **Relaxed-triangle distance** | \(d(x,z)\le c[d(x,y)+d(y,z)]\) | Quantified deviation from metric triangle | Standard metric-tree pruning or an HNSW theorem |
| **Divergence** | Directed discrepancy; e.g. KL/Bregman | Semantically natural directional retrieval | Symmetry or ordinary triangle |
| **PSD kernel** | Symmetric \(K\) with every Gram matrix PSD | Hilbert feature map; canonical feature-space pseudometric | That \(1-K\) is a metric |
| **Indefinite kernel/similarity** | Symmetric similarity with negative Gram eigenvalues possible | Useful similarity; Krein-space methods available | Hilbert norm or Euclidean metric |
| **MIPS** | Rank by \(q^\top x\), or \(\phi(q)^\top\psi(x)\) | Nonmetric vector ranking with mature ANN techniques | Triangle inequality |
| **General similarity/score** | Only an ordering objective is specified | Exact ranking is always meaningful | Any generic ANN acceleration |
| **Metric ranking / ordinal metric** | Score is a strict monotone transform of a known metric | Exactly the ordering HNSW needs in standard top-\(k\) comparisons | Arithmetic metric bounds under the transformed score |

The terminology around *semimetric* and *quasimetric* is genuinely inconsistent. Recent literature uses “semi-metric” for symmetric distances lacking triangle inequality, while other mathematical traditions attach different weakened axioms. Likewise, one body of quasi-metric literature uses the term for an asymmetric distance satisfying directed triangle inequality, while another uses “quasimetric” for a relaxed triangle inequality with multiplicative constant. citeturn19academia3turn18academia1turn19academia2

**Nexus should therefore not expose `SEMIMETRIC` or `QUASIMETRIC` as self-explanatory enum values.** The contract should name the actual property, such as `SYMMETRIC_NO_TRIANGLE`, `DIRECTED_TRIANGLE`, or `C_RELAXED_TRIANGLE`.

### Cosine is the canonical warning case

For nonzero vectors,

\[
s_{\cos}(x,y)=\frac{x^\top y}{\|x\|\|y\|}.
\]

On unit-normalized vectors, several quantities are closely related but not mathematically identical:

\[
d_{\text{raw}}(x,y)=1-\cos(x,y),
\]

\[
d_{\text{angle}}(x,y)=\arccos(\cos(x,y)),
\]

\[
d_{\text{chord}}(x,y)
=\|x-y\|
=\sqrt{2-2\cos(x,y)}.
\]

Angular distance on the unit sphere is a metric, as is chordal Euclidean distance. By contrast, \(1-\cos\) is half the **squared** chordal distance and does not satisfy ordinary triangle inequality in general. This is consistent with the literature's warning that cosine-derived quantities should not casually be treated as metrics. citeturn10academia36

A three-point counterexample is immediate. Put three unit vectors at angles \(0^\circ,60^\circ,120^\circ\). Then

\[
d(0,120)=1-\cos120^\circ=\frac32,
\]

but

\[
d(0,60)+d(60,120)
=
\frac12+\frac12
=1,
\]

so

\[
\frac32>1.
\]

Yet this triangle failure is **irrelevant to standard HNSW's ordering** on these normalized vectors because

\[
1-\cos\theta,\qquad
\arccos(\cos\theta),\qquad
\sqrt{2-2\cos\theta}
\]

are all strictly increasing functions of the angle on \([0,\pi]\). Faiss operationalizes exactly this relationship: it recommends normalizing database and query vectors and using maximum inner product, noting that on normalized vectors

\[
\|x-y\|^2=2-2\langle x,y\rangle .
\]

citeturn22view0turn22view1turn22view2

This yields a major Nexus rule:

> **[ESTABLISHED MATHEMATICS / ALGORITHM PROPERTY] Failure of triangle inequality in the raw numeric representation is not, by itself, evidence that a ranking is unsuitable for HNSW. First test whether the score is a monotone transform of a sound metric geometry.**

hnswlib itself makes the same point operationally without naming it as such: its “L2” callback is squared L2, and its cosine callback is \(1-\cos\); neither fact prevents HNSW from operating because the relevant nearest-neighbor order is preserved. citeturn21view0

### PSD, CND, and indefinite similarities

For a symmetric PSD kernel \(K\), there exists a Hilbert-space feature map \(\phi\) with

\[
K(x,y)=\langle\phi(x),\phi(y)\rangle.
\]

The canonical induced distance is therefore

\[
d_K(x,y)
=
\sqrt{
K(x,x)+K(y,y)-2K(x,y)
}
=
\|\phi(x)-\phi(y)\|.
\]

This is a pseudometric in general and becomes a true metric when the feature representation separates points. **PSD kernel \(\neq\) metric automatically;** rather, PSD supplies a Hilbert representation from which a metric or pseudometric can be constructed.

A conditionally negative-definite dissimilarity is another useful *transformability* certificate. Under the standard zero-diagonal negative-type conditions, such a dissimilarity corresponds to a squared Hilbert distance, so its square root has Hilbert metric geometry. Negative-definite structure is consequently useful when Nexus wants a principled Euclidean/Hilbert reduction, but it is not an HNSW requirement. Modern work continues to exploit negative-definite distances to construct PSD kernels and Hilbert representations. citeturn20academia36turn20search2

An indefinite kernel is different. Indefinite similarities can be mathematically meaningful and can be treated in reproducing-kernel Krein spaces, but the ordinary Hilbert-space PSD interpretation is lost. Oglic and Gärtner explicitly develop scalable methods for such indefinite similarities rather than pretending they are PSD kernels. citeturn20search0turn20search9

### Monotone transforms deserve first-class status

Suppose

\[
\rho(x,y)=f(d(x,y))
\]

where \(d\) is a metric and \(f\) is strictly increasing. Then

\[
d(x,a)<d(x,b)
\iff
\rho(x,a)<\rho(x,b).
\]

For standard top-\(k\) HNSW, the search and construction algorithms use priority ordering and pairwise comparisons rather than metric-tree-style arithmetic lower bounds. The original neighbor-selection heuristic, for example, compares candidate-to-query and candidate-to-selected-neighbor distances in deciding whether a new edge contributes diversification. A strictly increasing transform preserves such inequalities. citeturn3view1turn4view2

Thus **metric ranking** is a materially different contract from arbitrary nonmetric scoring:

\[
\text{metric}
\subsetneq
\text{metric ranking}
\subsetneq
\text{general ranking}.
\]

The first inclusion is strict because squared Euclidean and \(1-\cos\) on normalized data are metric rankings without themselves being metrics.

This also explains why triangle inequality matters very differently to a metric tree. An M-tree is explicitly derived for a space whose distance satisfies positivity, symmetry, and triangle inequality; its safe pruning uses those numerical bounds. A monotone nonlinear transform can therefore invalidate the pruning arithmetic even while preserving nearest-neighbor ordering. citeturn17search4

## What HNSW actually requires: theorem, heuristic, implementation, and evidence

### The original algorithm

The original HNSW paper frames the nearest-neighbor problem in terms of a supplied distance and presents HNSW as a method applicable to general metric-space search, but the executable algorithms themselves use distance evaluations to guide greedy/beam traversal and to select neighbors; they do not invoke an explicit triangle-inequality pruning bound. citeturn2view0turn3view1turn3view2

Its graph quality depends on two related ideas:

\[
\text{hierarchical long-range navigation}
+
\text{diversified local connectivity}.
\]

The construction heuristic does not merely retain the \(M\) closest candidates. It compares candidates with already selected neighbors, approximating relative-neighborhood-style diversification and helping avoid redundant edges and local minima. citeturn4view2

This is where geometry matters, but it matters through **neighborhood topology**, not through a line of code reading `assert(triangle_inequality)`.

The decisive evidence is the original paper's own section on “general spaces.” It explicitly describes these as spaces that can be nonsymmetric or violate triangle inequality and tests HNSW on examples including cosine-related data, Jensen-Shannon-style comparisons, SQFD, and edit-distance-oriented datasets. It reports that HNSW substantially improved over the earlier NSW graph method, including a very large improvement on one Jensen-Shannon benchmark, and concludes that the algorithm is applicable in generalized metric/nonmetric settings. citeturn5view0turn5view1turn5view2

Therefore:

> **“HNSW requires triangle inequality.” — FALSE as an algorithm-execution statement and FALSE as a description of the original empirical scope.**

But the stronger statement—

> **“HNSW therefore works reliably for arbitrary scores.”**

—does not follow.

### What comparison-based HNSW needs

For ordinary top-\(k\) operation, a practical HNSW geometry needs at least the following.

**[ALGORITHM REQUIREMENT] Pairwise comparability.** HNSW must be able to rank candidates relative to a query and, during construction/diversification, compare stored points with other stored points. A score defined only for a special semantic pair such as “evidence \( \to \) hypothesis” but not meaningfully between two hypotheses is therefore **not directly a self-contained HNSW graph geometry**.

**[IMPLEMENTATION REQUIREMENT] Stable numeric ordering.** Real implementations need finite, consistently ordered values; NaNs and unstable nondeterminism undermine queues and graph construction. pgvector, for example, requires finite vector components for its vector types. citeturn22view4

**[PERFORMANCE HEURISTIC] Neighborhood coherence.** Similar points should tend to lead to other useful points. The graph must contain routes by which local search can make progress. The original HNSW paper discusses false local minima as a core graph-search problem and uses hierarchy/diversification to mitigate them. citeturn3view0turn3view1

**[THEORETICAL CONDITION IN RECENT WORK] Navigability.** Recent NeurIPS work proves approximation guarantees for an adaptive graph beam search when the underlying graph is navigable, explicitly connecting this graph property to ANN performance. citeturn24view1

None of these is equivalent to the ordinary triangle inequality.

### Triangle inequality is neither necessary nor sufficient for fast HNSW

It is **not necessary** because the original nonmetric experiments, MIPS graph literature, and deployed implementations provide direct counterexamples. hnswlib explicitly supports inner product while noting it is not a metric; NMSLIB explicitly targets nonmetric spaces; pgvector's HNSW supports inner-product and cosine operators; and Lucene's vector-search stack supports maximum inner product. citeturn21view0turn15search4turn22view3turn23search0

It is also **not sufficient** for a strong HNSW guarantee. Indyk and Xu construct instance families where HNSW requires empirically linear query effort for reasonable accuracy, showing that broad graph-ANN performance guarantees do not fall out merely from conventional nearest-neighbor geometry. citeturn24view0

Other structural quantities can matter greatly. Elliott and Clark find HNSW recall linked to intrinsic dimensionality and report that insertion order can move recall by as much as twelve percentage points under their tested setup. This does not establish a universal causal law, but it demonstrates that graph construction quality is sensitive to dataset topology and insertion history even without changing the score function. citeturn25academia12

Thus the best classification is:

\[
\boxed{
\text{“HNSW depends on triangle inequality”}
=
\textbf{CONTEXT-DEPENDENT / PARTIALLY TRUE}
}
\]

only if “depends” is being used loosely to mean “often benefits from coherent geometric structure.” As a literal algorithm requirement, it is false.

### Why arbitrary nonmetric scores can still be dangerous

Graph search needs paths from entry regions toward high-ranking results. Consider an entry node \(e\), an intermediate \(u\), and the true best answer \(t\). A query score may yield

\[
d(q,e)=2,\qquad d(q,u)=3,\qquad d(q,t)=0,
\]

while the only graph path to \(t\) goes through \(u\). Pure greedy routing stops at \(e\), because the first step looks worse. A beam can sometimes escape, but sufficiently adversarial ranking landscapes can generate many such basins.

That phenomenon is not uniquely caused by triangle violation: even a metric graph can be badly wired. The more precise failure is **lack of a monotonic or beam-navigable path**. This is why “count triangle violations and infer HNSW recall” is theoretically weak.

The metric-tree case is qualitatively different. Suppose a tree uses the metric lower bound

\[
d(q,x)\ge |d(q,p)-d(x,p)|.
\]

If a nonmetric score has

\[
d(q,p)=10,\qquad
d(x,p)=1,\qquad
d(q,x)=1,
\]

the metric-derived bound falsely claims \(d(q,x)\ge9\). A pruning algorithm can then discard the subtree containing the true nearest neighbor. That is a **correctness failure caused directly by violating the theorem's assumption**, not merely a likely degradation in recall. M-tree's specification explicitly assumes positivity, symmetry, and triangle inequality for precisely this kind of metric indexing. citeturn17search4

This distinction should be canonical in Nexus:

| Status | Meaning |
|---|---|
| **Algorithm requires property** | Violating it can invalidate correctness/pruning logic |
| **Implementation accepts property violation** | Code can evaluate and run |
| **Heuristic benefits from structure** | Quality or efficiency may improve, without correctness theorem |
| **Empirically validated** | A tested workload met a recall/latency target |
| **Mathematically proved geometry** | The configured score belongs to a known class |
| **Nexus design preference** | Architectural safety rule, not a mathematical theorem |

### The adversarial case against being conservative

The strongest case **against** imposing metricity on HNSW is substantial.

First, the original HNSW authors intentionally tested generalized/nonmetric spaces rather than accidentally wandering into them. citeturn5view0turn5view1

Second, modern HNSW implementations intentionally expose nonmetric inner product and cosine-style dissimilarities. citeturn21view0turn22view3turn23search0

Third, MIPS research has demonstrated that nonmetric similarity graphs can work extremely well. Morozov and Babenko explicitly build similarity graphs for MIPS and report that direct nonmetric graph search can outperform reductions to ordinary nearest-neighbor geometry; they argue that some metric reductions are actually detrimental to the graph topology used by similarity search. citeturn24view3

Fourth, specialized graph work such as Möbius-transformed inner-product search exists precisely because nonmetric MIPS graph topology can be exploitable rather than pathological. citeturn24view4

Fifth, some apparently “nonmetric” HNSW scores are merely monotone transforms of metrics. Rejecting \(1-\cos\) or squared L2 because the raw formula fails triangle inequality would be mathematically formalistic but algorithmically pointless for a comparison-based top-\(k\) graph.

So a Nexus rule of “HNSW only for literal metrics” would be unnecessarily conservative.

The equally strong case **against** complete permissiveness is that direct MIPS has motivated specialized graph construction precisely because generic metric-oriented graph topology is not always ideal; nonmetric Bregman ANN requires additional structural assumptions and specialized indexing; and HNSW's own worst-case guarantees remain weak. citeturn24view3turn18academia2turn18academia3turn24view0

The correct compromise is therefore **typed permissiveness plus empirical proof of retrieval quality**, not either universal prohibition or universal acceptance.

## Nexus geometry for HTLA, cross-label HTLA, and HTNLA

### Aligned-label HTLA

For

\[
\langle H,K\rangle_w
=
\sum_\ell w_\ell\langle H_\ell,K_\ell\rangle,
\]

if

\[
w_\ell>0\quad\forall \ell,
\]

then this is an ordinary inner product on the direct sum. The induced norm is

\[
\|H\|_w
=
\sqrt{\sum_\ell w_\ell\|H_\ell\|^2}
\]

and

\[
d_w(H,K)=\|H-K\|_w
\]

is a true metric.

Equivalently, define

\[
B=\operatorname{diag}(\sqrt{w_1}I,\ldots,\sqrt{w_L}I).
\]

Then

\[
\langle H,K\rangle_w
=
\langle BH,BK\rangle,
\]

so aligned-label HTLA is simply Euclidean/Hilbert retrieval after a known linear scaling.

If instead \(w_\ell\ge0\) and some weights vanish, the construction yields a seminorm and a pseudometric: states differing only in zero-weight blocks can have distance zero.

**Nexus recommendation — high confidence:** ordinary HVD aligned-label retrieval should expose this strongest known geometry rather than merely advertise “custom similarity.”

For normalized nonzero \(BH\), Nexus has several legitimate representations of the same ordering:

\[
\text{weighted cosine similarity}
\leftrightarrow
\text{angular metric}
\leftrightarrow
\text{normalized chordal metric}
\leftrightarrow
\text{normalized inner product MIPS}.
\]

Faiss's recommended normalized-inner-product treatment of cosine and Lucene's recommendation to use dot product on normalized vectors are consistent with this design. citeturn22view2turn23search0

A robust declaration would therefore be something like:

```text
retrieval_kind: METRIC_RANKING
canonical_metric: WEIGHTED_CHORDAL
score: WEIGHTED_COSINE
normalization: UNIT_WEIGHTED_NORM
proof: POSITIVE_DIAGONAL_WEIGHT_CONSTRUCTION
```

rather than calling \(1-\cos\) itself a metric.

### Cross-label bilinear HTLA

Write the configured cross-label score as

\[
C_W(H,K)=H^\top A_WK.
\]

The mathematical cases are sharply different.

| \(A_W\) | What is established | Canonical retrieval interpretation |
|---|---|---|
| \(A=A^\top\succ0\) | Genuine inner product \(H^\top AK\); norm and Mahalanobis/Euclidean metric | Shared Hilbert embedding; metric ANN or cosine after valid normalization |
| \(A=A^\top\succeq0\), singular | PSD kernel; shared feature map; seminorm/pseudometric | Hilbert pseudometric / PSD-kernel ranking |
| \(A=A^\top\) indefinite | Indefinite bilinear similarity; no Hilbert norm from \(H^\top AH\) | Indefinite similarity or asymmetric-factor MIPS |
| \(A\ne A^\top\) | Directed bilinear score | Directional MIPS / compatibility ranking |
| Nonlinear \(C(H,K)\) with no proved structure | General compatibility | Exact/general-score retrieval unless a specialized ANN contract is established |

For symmetric PSD \(A\), factor

\[
A=B^\top B.
\]

Then

\[
H^\top AK
=
(BH)^\top(BK).
\]

If \(A\) is positive definite, \(B\) is injective and

\[
d_A(H,K)
=
\sqrt{(H-K)^\top A(H-K)}
\]

is a metric. If \(A\) is merely PSD, it is a pseudometric on the original state space and a metric after quotienting out the null space.

**[ESTABLISHED MATHEMATICS]** This is the cleanest condition under which Nexus may legitimately upgrade “cross-label compatibility” into a shared inner-product geometry.

If \(A\) is indefinite, the common expression

\[
\frac{H^\top AK}
{\sqrt{H^\top AH}\sqrt{K^\top AK}}
\]

is **not a canonical cosine**, because self-quadratic values may be zero or negative. Indefinite-kernel methods exist, but that fact does not create a Hilbert norm. citeturn20search0turn20search9

If \(A\neq A^\top\), symmetrizing it,

\[
A_{\mathrm{sym}}
=
\frac{A+A^\top}{2},
\]

generally changes the retrieval semantics:

\[
H^\top AK
\ne
H^\top A_{\mathrm{sym}}K.
\]

The antisymmetric component contains exactly part of the directionality that a source-to-target compatibility relation may be intended to express. **Symmetrization is therefore a semantic operation, not a harmless ANN optimization.**

### A crucial fact: every finite-dimensional bilinear score is MIPS-compatible

PSD is **not** necessary to exploit vector ANN.

For any fixed matrix \(A\),

\[
s(q,x)=q^\top Ax
\]

can be written as an ordinary inner product between different query and database representations. The simplest algebraic form is

\[
s(q,x)
=
(A^\top q)^\top x.
\]

More symmetrically, take an SVD

\[
A=U\Sigma V^\top
\]

and define

\[
\phi(q)=\Sigma^{1/2}U^\top q,\qquad
\psi(x)=\Sigma^{1/2}V^\top x.
\]

Then

\[
q^\top Ax
=
\phi(q)^\top\psi(x).
\]

This works even when \(A\) is nonsymmetric. For a symmetric indefinite \(A\), an analogous signed factorization gives distinct query/data embeddings.

Therefore the right Nexus conclusion is:

> **PSD determines whether cross-label compatibility is a shared Hilbert geometry. It does not determine whether the score is reducible to MIPS.**

That distinction is extremely valuable architecturally.

A directional bilinear score can be:

```text
retrieval_kind: MIPS
query_transform: phi
database_transform: psi
shared_geometry: false
directional_semantics: true
```

without ever claiming that it is a metric.

MIPS itself does not require triangle inequality. Asymmetric LSH work established sublinear MIPS schemes using different query and data transformations, and later graph work directly builds nonmetric similarity graphs for the problem. citeturn11search0turn24view3

There is, however, an important systems caveat. An algebraic reduction preserving

\[
q\mapsto\operatorname{rank}\{s(q,x_i)\}
\]

does not necessarily preserve the **database-to-database graph topology** that makes a particular graph ANN method easy to navigate. Morozov and Babenko specifically report that nearest-neighbor reductions can be detrimental for similarity-graph MIPS, while Zhou et al. construct a graph transformation tailored to inner-product search. citeturn24view3turn24view4

So Nexus should separate:

\[
\text{exact score equivalence}
\]

from

\[
\text{ANN topology equivalence}.
\]

The former can be a theorem; the latter generally needs algorithm-specific analysis or benchmarking.

### Truly asymmetric distances and divergences

An asymmetric score is **not** automatically a quasimetric.

To qualify for a directed-triangle geometry under the common asymmetric definition, Nexus must establish something like

\[
d(x,x)=0,\qquad
d(x,y)\ge0,
\]

and

\[
d(x,z)\le d(x,y)+d(y,z),
\]

without requiring \(d(x,y)=d(y,x)\). Quasi-metric literature explicitly studies similarity search under this asymmetric geometry. citeturn18academia1

KL/Bregman-style divergences show why this category must remain distinct. They can be asymmetric and need not satisfy ordinary triangle inequality, yet provable ANN algorithms have been constructed specifically for Bregman divergences using properties other than ordinary metricity. Abdullah, Moeller, and Venkatasubramanian describe ANN algorithms extending beyond distances that are symmetric or triangle-inequality respecting, and subsequent work derives lower bounds depending on Bregman structural constants. More recent fixed-dimensional work likewise provides ANN structures for Bregman divergences, including KL and Itakura-Saito, under smoothness/growth assumptions. citeturn18academia2turn18academia3turn18academia0

That is decisive evidence for a broader principle:

> **Nonmetric does not mean unindexable. It means that the index's theorem and construction must match the actual nonmetric structure.**

Standard HNSW can be empirically attempted on such scores—the original paper even tested generalized spaces—but Nexus should not translate this into a universal directed-distance contract.

### HTNLA and learned geometry

A learned transformation adds a second axis of risk: the retrieval geometry itself can change with model generation.

Suppose

\[
z=T_g(H)
\]

for generation \(g\), with indexed geometry

\[
d_g(H,K)=d(T_g(H),T_g(K)).
\]

Changing to \(T_{g+1}\) can alter:

- pairwise distances;
- nearest-neighbor rankings;
- local intrinsic dimensionality;
- graph edge quality;
- query-to-database compatibility;
- normalization statistics.

Because HNSW graph construction encodes historical pairwise orderings, an old graph is not automatically valid under a new transform. The empirical sensitivity of HNSW to intrinsic geometry and insertion order makes this more than a bookkeeping concern. citeturn25academia12

Accordingly, the Nexus invariant proposed in the brief should be strengthened:

\[
\boxed{
\text{representation generation}
+
\text{geometry-contract generation}
+
\text{index generation}
\text{ must be compatible}
}
\]

An index may remain reusable when a change is *proved* ranking-preserving—for example, a common orthogonal transform under Euclidean distance—but arbitrary learned-model upgrades should presumptively invalidate the index until compatibility is certified.

### Projection, quantization, and approximate geometry

Distance-preserving dimensional reduction provides a clean example of what a useful approximation guarantee actually looks like. Classical Johnson–Lindenstrauss-style projection preserves pairwise squared Euclidean distances of a finite set in \(O(\log n/\varepsilon^2)\) dimensions up to multiplicative distortion. citeturn25search2

Suppose for query \(q\) and every candidate \(x\),

\[
(1-\varepsilon)d(q,x)
\le
d'(q,x)
\le
(1+\varepsilon)d(q,x).
\]

For two candidates with \(d_i<d_j\), their order is guaranteed to survive whenever

\[
(1+\varepsilon)d_i
<
(1-\varepsilon)d_j.
\]

Equivalently,

\[
\frac{d_j}{d_i}
>
\frac{1+\varepsilon}{1-\varepsilon}.
\]

At the \(k\)-neighbor boundary, a sufficient ranking-stability condition is therefore

\[
\frac{d_{k+1}}{d_k}
>
\frac{1+\varepsilon}{1-\varepsilon}.
\]

This makes an important Nexus principle explicit:

> **Distance preservation does not imply exact nearest-neighbor ranking preservation when neighbors have small margins.**

If the ANN procedure in the projected space returns an \(\alpha\)-approximate neighbor, the same distortion assumptions imply approximately

\[
d(q,\hat x)
\le
\alpha
\frac{1+\varepsilon}{1-\varepsilon}
d(q,x^\star).
\]

Quantization and low-rank approximations need analogous error bounds when available; otherwise they require direct exact-baseline evaluation. Product-quantization literature explicitly uses asymmetric approximate distance calculations between an exact query and compressed database representations, illustrating that “asymmetric distance computation” in compression is not the same notion as an inherently asymmetric semantic distance. citeturn16academia46turn16search6

## Retrieval-geometry type system, index compatibility, and triangle recommendation

A single enum such as

```text
{ METRIC, NONMETRIC }
```

is insufficient. Equally, a flat enum mixing `PSD_KERNEL`, `MIPS`, and `QUASIMETRIC` confuses properties that can coexist.

A stronger Nexus contract is **two-layered**.

First declare the retrieval objective:

```text
RetrievalObjective =
    METRIC_NN
    PSEUDOMETRIC_NN
    METRIC_RANKING
    MIPS
    DIRECTED_DISTANCE_NN
    GENERAL_RANKING
```

Then attach proven capabilities:

```text
GeometryCapabilities {
    symmetric: true | false | unknown
    separating: true | false | unknown
    ordinary_triangle: proved | disproved | unknown
    directed_triangle: proved | disproved | unknown
    relaxed_triangle_constant: optional
    psd_kernel: proved | disproved | unknown
    cnd_or_negative_type: proved | disproved | unknown
    shared_hilbert_embedding: optional
    query_embedding: optional
    database_embedding: optional
    monotone_metric_base: optional
    normalization_contract: optional
}
```

This avoids false logical implications such as

\[
\text{PSD kernel}\Rightarrow\text{raw kernel is distance}
\]

or

\[
\text{asymmetric}\Rightarrow\text{directed triangle}.
\]

### Recommended index-compatibility matrix

Legend: **Yes** means natural contract; **Conditional** means mathematically executable but requires algorithm-specific validation; **No** means the conventional index's correctness assumptions are incompatible.

| Declared geometry | HNSW | Metric tree | IVF/PQ family | MIPS-specific method | Exact scan | Nexus default |
|---|---|---|---|---|---|---|
| **Euclidean / weighted Euclidean metric** | **Yes** | **Yes** | **Yes** | Optional | Yes | HNSW/IVF/PQ based on scale |
| **Angular/chordal metric** | **Yes** | Yes | Yes via normalized-vector methods | Yes via normalized IP | Yes | HNSW or angular-compatible ANN |
| **Metric ranking** such as squared L2 or \(1-\cos\) normalized | **Yes for comparison-based top-k** | **No using raw transformed value unless pruning rederived** | Conditional | Conditional | Yes | HNSW allowed with certified base metric |
| **Pseudometric** | Yes; handle equivalence/duplicates | Usually conditional on implementation | Conditional | Optional | Yes | Prefer quotient/canonical representatives where useful |
| **PSD kernel** | Via explicit feature distance or inner-product representation | Via induced metric/pseudometric | Conditional | Yes if represented as dot product | Yes | Materialize declared feature geometry |
| **MIPS** | **Yes empirically; no generic metric guarantee** | No | Yes for IP-aware variants | **Yes** | Yes | Dedicated MIPS contract |
| **Directed quasimetric** | Conditional/experimental | Conventional metric tree: no | Specialized only | Possibly | **Yes** | Specialized index or benchmarked HNSW |
| **Bregman/KL-type divergence** | Conditional/experimental | Conventional metric tree: no | Specialized structures | Specialized | **Yes** | Divergence-aware method |
| **Indefinite bilinear score** | Conditional; preferably factor as two-sided MIPS | No | Not as ordinary metric PQ | **Yes if finite-dimensional separable factorization** | Yes | MIPS if factorizable |
| **Arbitrary symmetric score** | Experimental only | No | Usually no | Only if transform exists | **Yes** | Exact or candidate+rereank |
| **Arbitrary directed compatibility** | Experimental and potentially semantically mismatched | No | No generic contract | If separable, convert to MIPS | **Yes** | Exact/rerank unless specialized contract |

Faiss is representative of why this classification should be algorithm-specific rather than philosophical. It supports L2 and inner-product retrieval directly, recommends normalized IP for cosine, provides transformations between some MIPS and L2 formulations, and offers HNSW alongside IVF/PQ families. citeturn22view0turn22view1turn10search6

DiskANN/Vamana should likewise be understood as a graph-ANN family with its own construction and performance regime rather than a magical fallback for arbitrary scores; the original DiskANN work establishes strong practical results, while later theory places particular guarantees under specific intrinsic-dimension and construction assumptions. citeturn24view2turn24view0

LSH also cannot be labeled “general nonmetric ANN.” Its guarantees depend on having a locality-sensitive family for the actual similarity/distance; asymmetric LSH was a specific technical development required to obtain sublinear MIPS search. citeturn11search0turn17search9

### Exact triangle-property recommendation for Nexus

There should be **no universal Nexus triangle axiom**.

Instead:

\[
\boxed{
\begin{array}{ll}
\texttt{METRIC\_NN}: &
\text{ordinary triangle required};\\[2mm]
\texttt{PSEUDOMETRIC\_NN}: &
\text{ordinary triangle required};\\[2mm]
\texttt{METRIC\_RANKING}: &
\text{raw triangle not required; certified monotone metric base required};\\[2mm]
\texttt{DIRECTED\_DISTANCE\_NN}: &
\text{directed triangle required only if the declared subtype promises it};\\[2mm]
\texttt{MIPS}: &
\text{no triangle requirement};\\[2mm]
\texttt{GENERAL\_RANKING}: &
\text{no triangle requirement, but no generic ANN entitlement}.
\end{array}
}
\]

A relaxed triangle inequality

\[
d(x,z)\le
c[d(x,y)+d(y,z)]
\]

may be useful metadata or a specialized algorithmic assumption, but it should **not** be promoted to a generic HNSW safety certificate. Literature uses such generalized triangle structures, but the reviewed HNSW theory does not provide a standard mapping from \(c\) to recall or query complexity. citeturn19academia2turn24view0turn24view1

Similarly, CND/negative type, PSD, doubling dimension, and intrinsic dimensionality should be capabilities or measured properties rather than substitutes for triangle inequality. They answer different questions:

- PSD: can the similarity be represented in Hilbert feature space?
- CND/negative type: can a dissimilarity be represented as squared Hilbert distance?
- doubling/intrinsic dimension: how complex is local geometric structure?
- navigability: can graph search actually progress efficiently?
- triangle inequality: are metric arithmetic bounds valid?

These are complementary, not interchangeable.

## Validation specification, engineering laws, gaps, and prioritized research agenda

Nexus needs three distinct validation layers. Conflating them would recreate exactly the ambiguity the research brief is trying to remove.

### Mathematical construction validation

This layer establishes properties by theorem or by construction.

For aligned HTLA, Nexus can verify configured weights:

\[
w_\ell>0
\]

to certify an inner product and metric, or

\[
w_\ell\ge0
\]

to certify PSD/pseudometric structure.

For a cross-label matrix \(A\), check exact or numerically robust structural conditions:

\[
\|A-A^\top\|
\]

for symmetry and the spectrum/Cholesky factorization for PSD. If \(A\succ0\), certify metric geometry. If \(A\succeq0\) but singular, certify pseudometric geometry.

For bilinear directional scores, construct and persist an explicit factorization

\[
A=U\Sigma V^\top,
\]

along with \(\phi,\psi\), and numerically verify on test vectors that

\[
H^\top AK
\approx
\phi(H)^\top\psi(K)
\]

within the floating-point error budget.

For a metric-ranking declaration, persist the base metric \(d\) and monotone transform \(f\), rather than merely asserting that empirical nearest-neighbor lists look similar.

**A finite sample cannot prove a universal metric, PSD-kernel, CND, or triangle property unless the underlying construction theorem already supplies that guarantee.** Sample tests can falsify or detect implementation/configuration errors; they cannot establish a universal axiom over an infinite state space.

### Numerical and adversarial property tests

Nexus should nevertheless run sampled diagnostics because configuration bugs are much more common than elegant counterexamples.

| Test | What it can detect | What it cannot prove |
|---|---|---|
| Finite-output test | NaN/Inf/domain failures | Geometric validity |
| Self-score / diagonal test | Unexpected \(d(x,x)\), norm problems | Identity globally |
| Symmetry residual \(|d(x,y)-d(y,x)|\) | Accidental directionality | Universal symmetry from finite samples |
| Triangle-violation distribution | Obvious nonmetric behavior | Universal triangle satisfaction |
| Empirical relaxed constant \(\hat c\) | Severity of sampled violations | Global \(c\)-triangle bound |
| Gram-matrix eigenvalues | PSD violations on sampled set | Kernel PSD over all possible states |
| CND centered-matrix check | Negative-type violations on sample | Global CND |
| Monotone-transform consistency | Broken implementation of certified metric ranking | Existence of unknown base metric |
| Bilinear factor reconstruction | Transform/configuration errors | Learned semantic quality |
| Perturbation/ranking stability | Fragile near-ties and numerical sensitivity | ANN recall on deployment distribution |

A particularly important warning is that **triangle-violation rate must not be used as an HNSW pass/fail gate in isolation.** Squared Euclidean and \(1-\cos\) can show genuine raw triangle violations while being order-equivalent to valid metrics; HNSW can behave identically under the corresponding monotone metric transform. citeturn21view0turn22view2

### Retrieval validation against exact semantics

For any approximate index lacking a theorem that directly covers the deployed score/data regime, the operational acceptance criterion should be exact-ground-truth retrieval.

At minimum, build an exact baseline under the **canonical Nexus semantic score**, not under the ANN proxy. Measure

\[
\operatorname{Recall@}k
=
\frac{
|\operatorname{ANN}_k(q)\cap\operatorname{Exact}_k(q)|
}{k}
\]

over representative and adversarial query strata.

For graded compatibility, also measure a relevance-sensitive ranking quantity such as NDCG or exact-score regret, because two top-\(k\) sets can have the same recall but materially different semantic quality.

The benchmark should sweep HNSW's search and construction parameters rather than certify one operating point. pgvector and hnswlib both document the basic recall/latency trade-off associated with larger `ef`/`ef_search`, while `ef_construction` changes build quality. citeturn21view0turn22view3

Nexus should additionally repeat construction under multiple insertion orders or seeds where the implementation permits it, because HNSW recall has been observed to vary materially with insertion sequence. citeturn25academia12

For directional retrieval, validation must use the real **query distribution**. A database graph that is excellent under candidate-to-candidate similarity may still be poorly aligned with \(\phi(q)^\top\psi(x)\) for deployed queries.

### Proposed index metadata and staleness contract

Every approximate index should bind at least:

```text
index_geometry_metadata {
    retrieval_objective
    canonical_score_id
    score_orientation          // lower-better / higher-better
    geometry_contract_version
    representation_generation
    query_transform_generation
    database_transform_generation
    normalization_contract
    metric_base_and_transform  // if METRIC_RANKING
    kernel_or_operator_hash
    dimensionality
    quantization_generation
    index_algorithm
    index_algorithm_version
    construction_parameters
    validation_dataset_id
    achieved_recall_contract
}
```

The invariant becomes:

\[
\boxed{
\text{query representation generation}
\sim
\text{score/geometry generation}
\sim
\text{index generation}
}
\]

where \(\sim\) means explicitly certified compatibility, not simply equality of vector dimensionality.

A model upgrade that changes \(T_g\), \(A_W\), normalization, projection, or quantizer should make the index stale unless Nexus can prove the change is retrieval-order preserving or has rerun the required validation.

### Candidate Nexus engineering laws

These are **NEXUS DESIGN CHOICES**, not mathematical theorems.

**Law of declared geometry.**
No ANN index shall be built from an undeclared retrieval objective and geometry contract.

**Law of semantic naming.**
A compatibility score shall not be exposed as a “distance” or “metric” unless its corresponding axioms are established.

**Law of ordinal geometry.**
A nonmetric score that is a certified strict monotone transform of a metric may be declared `METRIC_RANKING`; it shall not be falsely rejected merely because its raw values violate triangle inequality.

**Law of metric pruning.**
An index whose correctness or pruning theorem assumes triangle inequality may consume only a geometry satisfying that theorem's assumptions, not merely an empirically similar score.

**Law of graph ANN validation.**
For HNSW on geometry without a directly applicable approximation theorem, deployment requires measured recall against exact canonical ranking over a versioned workload.

**Law of directional preservation.**
Directional compatibility shall not be symmetrized solely to satisfy an ANN implementation. Any symmetrization must be an explicit semantic transformation.

**Law of MIPS distinction.**
A bilinear/separable compatibility objective shall be classified as MIPS when appropriate rather than disguised as metric NN.

**Law of shared-Hilbert proof.**
A cross-label operator may be advertised as a shared inner-product geometry only when symmetry and PSD are established.

**Law of generation binding.**
Every ANN index shall bind to the representation, geometry, transform, normalization, and quantization generations used to construct it.

**Law of canonical-state separation.**
An ANN result is a retrieval candidate, not canonical Nexus state; similarity is neither identity, truth, nor authorization. This preserves the conceptual distinctions mandated in the research brief. fileciteturn0file0

### Unresolved research questions

The most important open gap is **not** whether HNSW can run without triangle inequality; that question is settled empirically and by implementation evidence. The harder question is how to predict *before full benchmarking* whether a particular Nexus compatibility score will produce a navigable HNSW graph.

There is currently no convincing universal scalar diagnostic such as triangle-violation rate, PSD residual, or asymmetry magnitude that predicts HNSW recall across score families. Modern theory points toward navigability, while empirical studies point toward intrinsic dimension, graph construction, and data order. citeturn24view0turn24view1turn25academia12

A second open question is whether Nexus's particular cross-label operators have enough structure to admit a stronger retrieval theorem. For example, bounded-rank \(A_W\), bounded condition number, controlled query/database encoder mismatch, or low intrinsic dimensionality after the \(\phi/\psi\) factorization may enable stronger MIPS-specific guarantees.

A third question is whether a **directed HNSW variant** should become a first-class Nexus backend. The original HNSW results establish empirical viability in some nonsymmetric spaces, and quasi-metric/Bregman literature establishes that directed ANN is mathematically tractable, but standard bidirectional HNSW topology is not a generic theorem for arbitrary source-to-target compatibility. citeturn5view0turn18academia1turn18academia2

A fourth question concerns model evolution: Nexus could empirically measure a **geometry-drift certificate** between generations using top-\(k\) overlap, pairwise rank correlation, neighborhood churn, and exact-score regret. Such a certificate would not prove index validity, but it could help decide whether a full rebuild is mandatory.

### Prioritized next research program

The highest-value next experiment is a Nexus-specific controlled benchmark in which the **same underlying ordering** is represented by Euclidean distance, squared Euclidean distance, angular distance, chordal distance, and \(1-\cos\). Standard HNSW should, modulo floating-point/tie effects and implementation details, expose the expected invariance under monotone transforms. That experiment would permanently separate “raw metric axioms” from “HNSW ranking geometry.”

The second priority is an operator sweep over synthetic \(A_W\) classes: SPD, singular PSD, mildly indefinite, strongly indefinite, nonsymmetric low-rank, and fully random nonsymmetric. For every operator, compare exact ranking with direct HNSW, two-sided MIPS factorization, specialized MIPS graph search, and candidate-generation-plus-exact-rerank. Measure recall, navigability proxies, insertion-order variance, and query-dependent failure modes.

The third priority is to test whether sampled quantities—triangle violations, asymmetry, Gram-spectrum indefiniteness, local intrinsic dimensionality, hubness, and graph monotonic-path rate—predict recall. The key scientific objective should be identifying the **best predictor of graph navigability**, not proving that one preferred geometric axiom is universally necessary.

The fourth priority is generation drift: perturb or retrain HTNLA transforms and measure how quickly an HNSW graph built under \(g_1\) loses recall under \(g_2\). This would turn the proposed `geometry_contract_version` from architectural caution into a quantitatively calibrated lifecycle rule.

**Overall confidence: HIGH.** The strongest conclusions—HNSW does not require triangle inequality, raw metricity is not the correct universal HNSW admission test, aligned HTLA admits a rigorous Hilbert geometry under positive weights, bilinear cross-label compatibility should be separated into PSD/shared-Hilbert versus MIPS/directional cases, and arbitrary scores require exact-baseline empirical validation—are supported simultaneously by established mathematics, the original HNSW paper, modern theory, MIPS/nonmetric research, and current implementations. The lower-confidence frontier is predictive: the literature still does not supply a simple geometry statistic that can tell Nexus in advance how well HNSW will navigate an arbitrary HTNLA compatibility landscape. The canonical specification should therefore make **proof of geometry and proof of retrieval performance separate obligations** rather than attempting to replace one with the other.
